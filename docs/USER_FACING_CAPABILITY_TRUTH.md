## 允许发给另一个住户的功能（两项受约束功能）

### 1. 个人物品使用提醒 —— `lib/chat/coliving/personal-item-reminder.ts`

- 触发（原有窄命令，保留兼容）：住户发来 `提醒 阿川：使用我的个人物品前先问我`
  （允许标点与礼貌前缀的窄变体）。命中即直接发送，行为不变。
- 识别：**纯正则，不过模型**（有限正则只覆盖几组固定说法，**不等于全面的语义识别**；
  覆盖不到的自然表达仍走普通对话）；命令体夹带任何多余内容（理由、物品名、别的诉求）
  一律不认，落回普通对话或回一句短说明，**不发送**。
- 发给对方的正文是**写死的常量**：`使用室友的个人物品前，请先征得对方同意。`
  不含来源、住户原话、物品名、理由或额外要求——避免借物品名或备注夹带未开放的要求。
- 校验全过才发：同一栋房子、名册里唯一、姓名已确认、非本人、当前渠道有地址。
- 回给发起人一句短收据。**整条链路不调用 LLM。**
- 自然语言请求（**预览 → 确认**）：住户**明确让 AI 去提醒某位被点名的室友**、主题正好是
  「用我的个人物品前先问我」，但没按固定命令写时（例如「帮我提醒阿川用我的个人物品前先问我」，
  **点了名、意思也对，只是没有冒号**），不再回模板指引，而是落一条**发给发起人本人**的
  待确认预览：如实说「还没有发给阿川」、把**将要发出的那句固定正文原样摆出来**。
  住户回「确认」才发，回「取消」就不发。
  判定自带主题 / 请求语气 / 非讨论 / 非否定 / 非混合的闸：纯抱怨、评理、讨论/征询、未点名
  对象（「有人」「他」）、以及混合或其它未开放主题（卫生/头发、费用、规则、一般噪音等）
  一律不命中，仍走普通对话。

### 2. 夜间洗衣提醒 —— `lib/chat/coliving/night-laundry-reminder.ts`

- 触发：住户发来 `提醒 阿川：深夜别开洗衣机或烘干机`（允许标点与礼貌前缀的窄变体，
  例如「晚上不要用洗衣机」「别在深夜开洗衣机或烘干机」）。
- 识别：**纯正则，不过模型**（有限正则只覆盖几组固定说法，**不等于全面的语义识别**；
  覆盖不到的自然表达仍走普通对话）；命令体夹带任何多余内容（清理头发、分摊水费、全屋规矩、
  人身攻击、具体钟点等）一律整体不认，**零第三方出站**，只回一句短的结构化指引；
  既不是这条命令形态、也不是「明确让 AI 提醒指定室友」的其它深夜洗衣自由文本仍走普通对话。
- 发给对方的正文是**写死的常量**：
  `深夜使用洗衣机或烘干机容易影响他人休息，请尽量避开深夜时段。`
  不含来源、住户原话、具体钟点、自由理由或附带命令。
- 校验全过才发：同一栋房子、名册里唯一、姓名已确认、非本人、当前渠道有地址。
- 回给发起人一句短收据。**整条链路不调用 LLM。**
- 近似请求（**预览 → 确认**）：住户**明确让 AI 去提醒某位被点名的室友**、主题正好是
  深夜洗衣，但没按固定命令写时（例如「帮我提醒阿川深夜别开洗衣机」，点了名、意思也对，
  只是没有冒号），不再只回模板指引，而是落一条**发给发起人本人**的待确认预览：如实说
  「还没有发给阿川」、把**将要发出的那句固定正文原样摆出来**，带「确认 / 取消」。
  住户回「确认」才发，回「取消」就不发。
  判定自带主题 / 请求语气 / 非讨论 / 非否定 / 非混合的闸：纯抱怨、评理、讨论/征询、未点名
  对象（「有人」「他」）、以及混合或其它未开放主题（一般噪音、卫生/头发、费用、规则等）
  一律不命中，仍走普通对话。
- 只处理「深夜运行洗衣机 / 烘干机影响别人休息」这一件共同影响，**不要求 AI 先裁定
  谁的卫生阈值或物品所有权**；不能从它外推到一般噪音、一般清洁、规则制定、费用或去留协调。

## 两项功能都有「近似请求」的预览 → 确认入口（不构成自由文本执行）

> 2026-09-12 重做：老板驳回「只回模板指引、要住户自己改写」的旧行为。近似请求现在
> 收口到**预览 → 确认**：AI 先把要发给谁、发哪一句固定正文如实摆出来（这条预览**只发给
> 发起人本人**），住户回「确认」才真的发，回「取消」就不发。
> **识别到近似请求本身绝不构成发给别人的授权**——凭据是落库的待确认提案**加上住户
> 明确回「确认」**，不是助手的文本、也不是进程内存。

- 住户没按固定命令写、但**明确让 AI 去提醒某位指定室友**、且主题正好是这两件事之一
  （「用我的个人物品前先问我」/「深夜别开洗衣机或烘干机」）时，走一个**确定性**入口：
  落一条**发给发起人本人**的待确认预览（点名收件人 + 原样摆出将发出的固定正文 +
  「确认 / 取消」），**零第三方出站、零模型调用**。
- **发送权只属于落库的待确认提案 + 住户的明确「确认」**：住户回「确认」后，系统按
  **原子的一次性认领**（单条 `UPDATE`，`status='sent'`、未回应、且正是会话里最新一条
  待确认出站、且在 24h TTL 内）认领提案，认领成功才真的写入那条固定第三方消息。
  并发或重复的「确认」只有一次能认领成功。`status='sent'` 是**项目侧投递状态**，
  **不代表对方已读**；这里的「只发一次」也只指同一条提案在项目侧只被认领一次，
  **不等于整个短信网络（Twilio 投递/重试）的 exactly-once**。
- 认领后发送前还要逐项核对：正文与当前固定文案**逐字一致**、收件人**仍在当前名册**且
  当前渠道可达、提案与当前会话/渠道**绑定**、最新一条出站**确实就是这条预览**。任一不过
  就**不发**，如实回一句真话（失效 / 发送状态无法确认），绝不谎报成功，也不会退回去重发造成重复。
- 认领后写入失败时，失败可能落在第三方**已入队之后**，所以只如实说**发送状态暂时无法
  确认、不会自动重发**——既不断言「没发出去」，也不叫住户重说一遍（那会诱发重复）。
- 「确认 / 取消」**只认整条消息就是那几个词**；「可以」「同意」「好的」这类别处也常用的
  词不算确认，「确认？」「确认，但别提到我」这类疑问或混合内容一律不认，绝不因歧义触发发送。
- **同一时刻只允许一条待确认提案**：落新预览前先作废该发起人 / 渠道 / 房子里所有还没回应
  的旧提案，避免后来说的「确认」把一条更旧的翻出来发掉。
- 判定纯字符串：只在「显式请求 AI 去提醒 + 名册里确有被点名的室友 + 该功能独有主题 +
  不是合规命令」同时成立时才命中。纯抱怨、评理、讨论/征询、未点名对象（「有人」「他」）、
  一般噪音、卫生/头发、费用、规则、混合议题等**一律不命中**，仍走现有普通对话——宁可靠
  漏掉一些自然表达，也不吞掉普通谈话；混合或否定请求**绝不**被拆成半边提案。
- 真正发给别人的第三方消息仍然只有两项功能的**写死正文**；预览只产生给当前说话人的
  待确认消息，不产生任何发给别人的消息。

## 现在明确做不到的（住户能感知）

- **一般噪音 / 深夜噪音提醒（非洗衣）**：只能提醒「深夜别开洗衣机或烘干机」这一件；
  说话声、搬家具、电视音量等其它噪音仍不能替住户私下提醒。
- **卫生整改 / 清理头发**：不能替住户要求室友「洗完澡清掉浴室墙面与地漏里的头发」。
  现场程度的卫生整改**仍未开放**。
- **任何代转达、代问、催办、协调**：不能把住户的话替转给另一个住户。
- **群体联系 / 群发**：不能分别联系多个住户，也不能替一群人约谈某个人。
- **主动发起**：cron 的四类主动作业（回访、问全规则、接触新住户、到期提醒）全部停用；
  房东入库也不再收到第一条消息。住户不开口，AI 不主动发。
- 遇到上面这些请求，AI 只能在**跟当前说话人**的对话里回复，并如实说明这件事它没法
  替对方发出去；**不能用自由文本假装已经联系过对方**——命中
  `claimsUnsentThirdPartyContact` 时，那句话会被替换成一句说真话的未发送说明。

## 为什么是这些、不是别的

老板 2026-09-12 选严格口径：立刻收回所有自由文本的第三方出站，只保留**程序化受约束**的
功能，并按「具体功能」逐项开放。夜间洗衣提醒即按这条路径成为第二项：它**不是**恢复了当初
被收回的自由文本出站，而是又一个写成受约束模块的窄功能（见 `.claude/CONCRETE_FUNCTIONS.md`）。
卫生整改、一般噪音、代转达、群体联系、cron 主动发起等**仍然明确不开放**——不是被遗忘，
是要开放必须逐项走同一条评审，不能靠恢复通用工具或自由文案蒙混回来。
