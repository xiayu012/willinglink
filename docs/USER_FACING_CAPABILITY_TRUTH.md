# 用户可见能力真相（对外能力边界单点事实源）

> 用途：回答一个具体问题——**AI 现在到底能替住户对「别人」做什么。**
> 涉及第三方出站、代转达、主动联系人、cron 主动发起的改动，先读本文件。
> 建立于 2026-09-12 老板「具体功能逐项开放」严格口径。
> 同目录相关：`.claude/CONCRETE_FUNCTIONS.md`（具体功能总册）、`.claude/PROJECT_STATE.md`。

> **2026-09-13 定稿（本文件的当前口径）**：老板把三个层次分清楚了——
> **任务能力**是一批**功能**的集合；**功能**是老板批准的**最小产品单位**（目前只有
> 「个人物品使用提醒」「夜间洗衣提醒」两件），像传统软件一样**各写各的朴素代码**，
> 允许重复、不强行抽象；**工具只是底层机械动作**——**功能不是工具**。主生成的工具表里
> **既没有短信工具、也没有功能工具**：住户自然说话时，`turn.ts` 在 `buildContext` 之后、
> 主生成之前走一条**功能前门**，对照**代码里写死的清单**（`features.ts` 的
> `APPROVED_FEATURES`），由**一次内部白名单路由**（不是每个功能各判一次）回答「是不是
> 明确交办清单里的某一项」；命中**恰好一个**才执行，只抽取**本功能获准的有限结构字段**
> （枚举 / 布尔，例如设备类别、时段、有没有用完归位——**不放任意的原始细节**）交给模型
> 写一句自然正文（**生成阶段看不到原始混合请求，也看不到来源情境**），再由**纯代码的投递服务**
> （`sms-delivery.ts`）绑定原话点名且唯一的收件人并落库。命中轮**不进主生成、不调任何
> 工具**（`toolsUsed` 为空）。路由器另有**第三个保留结果 `reply_only`**：请求明确围绕
> 某项功能，但这一轮是否定 / 征询 / 附条件 / 同时交办两件、不能立即执行——它不是功能、
> 不是工具，走一条**无工具、无出站**的小回复，只跟当前说话人讨论「这一轮不动作」。
> 不新增 LLM tool、不做 action card / proposal / functionId
> 工具选择仪式、也不写死正文常量。
> 下面是这一版的口径；2026-09-12 的「纯正则 + 写死常量」、其后的「动作卡 / proposition」、
> 以及中间那版「唯一共享工具 `sendRoommateMessage`」都是**已被驳回的历史**，不再描述当前行为。

  `JIJYUN_WEBHOOK_URL`、私信模型 `XHS_DM_MODEL`、`CHANNELS` 里的 `xhs` 全部去掉。

  `web` / `sms`（不含 wecom、xhs）；企业微信的运行文件、`package.json` 自检命令、
  `proxy.ts` 路由与运行时代码里的 `wecom` 字面量均已清除；小红书私信的四条运行

  投递与两项已批准功能（个人物品、夜间洗衣）仍可投递。

## 允许替住户发给另一个住户的功能（两项已批准功能）

两项功能**各写各的朴素模块**，但共用**同一个功能前门**与**同一个纯代码投递服务**。

数据流（关键：**生成阶段看不到原始混合请求**）：

```
住户原话
  → 代码绑定收件人  resolveNamedRecipient（原话点名且唯一；不唯一/没点名/点自己 → 前门不启动）
  → 一次白名单路由   routeApprovedFeature（内部模型只从代码清单 id 里选一个、none、或 reply_only）
                     （none / 清单外 → 落回普通对话，零出站；路由用量照计）
  → 命中功能 extract（只抽取本功能获准的有限结构字段）→ 模型写正文与短回执（compose；看不到原话、夹带诉求与来源情境）
  → 纯代码 deliverSms（可达性 + assertCanWrite 硬闸 → recordDecision → 入队 → 落库出站）
  → 或 reply_only    generateReplyOnlyReply（无工具、无出站，只回当前住户一两句；用量照计）
```

1. 住户**明确交办**这两件事之一、并**点名**名册里恰好一位非本人同住人时，功能前门才启动。
   前置的收件人绑定是**纯代码**判定（`resolveNamedRecipient`：名册里名字被原话点名、且
   唯一、且不是发起人）——**不判断主题**，所以它不会替模型认主题。
2. **功能识别靠模型、不写穷举中文正则，但只调一次**：`features.ts` 发起**一次**内部
   白名单路由调用，路由器只能在 `APPROVED_FEATURES` 的 id 里选一个、`none`、或保留结果
   `reply_only`。它**不是
   LLM tool、不暴露给主 agent、不新增 tool schema**；命中后也只调**被选中那一个功能**的
   `extract` 抽取**本功能获准的有限结构字段**（设备类别 / 时段 / 是否影响休息；哪件物品 /
   用完有没有归位——**都是枚举或布尔，不收任意原文**）。路由用生产模型
   `deepseek/deepseek-v4.1-flash`，temperature 0。**清单写死在代码里**，清单外的主题
   根本不会被选中。这样清单里加到 20 项，一条消息也仍然只多一次路由调用，而不是 20 次。
3. **正文由模型写**（不是写死常量、不要求按命令说话、不做二次确认）：生成阶段只拿到
   **收窄后的有限字段**——它看不到原始混合请求、看不到夹带的其它诉求、也看不到来源情境
   （谁提出来的、是谁被打扰、原话里的时间或空间细节）。因此模型不可能把这些写进正文。
   提示词明确要求**第三人称、中立的协调员口吻**：AI 是替这栋房子传话的协调员，不是受影响
   的住户，绝不能写「我被吵醒」「我房间」「我的东西」；也**不得凭空断言当前时间 /「今晚」/
   「已经发生」**——时段字段只表示"希望对方避开"，不代表"现在就是那个时段"。正文短、
   自然、有理由、说清请对方怎么做；短回执也由模型写，为空时才回落到本功能的兜底短句。
4. 纯代码投递服务 `deliverSms` 在发送前最后核一遍：收件人必须是原话点名且唯一的那位
   （模型改不了人）；**可达性**（姓名已确认、当前渠道有地址）不满足就回一句真话、零写入；
   落任何写入都过 `assertCanWrite` 发送硬闸。

### 1. 个人物品使用提醒

- 主题：**用我的个人物品前先问我。**
- 触发（自然语言即可）：住户点名一位室友、明确要 AI 去提醒、说的正好是这一件事。
  典型：「阿川昨天没跟我说一声就拿了我放在客厅的充电器用，用完也没放回去。你帮我
  跟他说一下，以后要用我的东西先问我。」旧窄命令形态（「提醒 阿川：使用我的个人物品
  前先问我」）仍然可用，但**不再是唯一入口**。
- 发给对方的正文由模型写，例如「阿川，室友的个人物品他有时候自己也要用，你用之前先
  跟他说一声，方便他安排，谢谢。」——**第三人称、中立协调员口吻、有理由、有具体请求**，
  不是冷命令；也**不会用第一人称冒充物品主人**（不提「我的东西」「我搁在」，也不点名
  是谁提出来的）。
- 判据模块：`lib/chat/coliving/personal-item-reminder.ts`。

### 2. 夜间洗衣提醒

- 主题：**深夜别用洗衣机或烘干机。**
- 触发（自然语言即可）：住户点名一位室友、明确要 AI 去提醒、说的正好是这一件事。
  典型：「阿川昨天凌晨四点开洗衣机和烘干机，机器就挨着我房间那面墙，我被吵醒了。
  你能不能私下跟他讲一下，这一次先别在深夜洗和烘干。」
- 发给对方的正文由模型写，例如「阿川，深夜开洗衣机或烘干机的声音会吵到休息，麻烦你
  尽量避开深夜时段，谢谢。」
- 只处理「深夜运行洗衣机 / 烘干机影响别人休息」这一件共同影响，**不要求 AI 先裁定
  谁的卫生阈值或物品所有权**；不能从它外推到一般噪音、一般清洁、规则制定、费用或
  去留协调。**电视音量（corpus-029）不属于这两件事**：路由返回 none，功能前门根本不
  执行——**零第三方出站**，这轮落回普通对话。
- 判据模块：`lib/chat/coliving/night-laundry-reminder.ts`。

## 两道保护：功能前门不启动 / 启动了也发不出去

**第一道：功能前门**（代码清单 + 一次白名单路由，命中才执行；其余一律落回普通对话）：

1. **不在清单上的主题**：卫生 / 清理头发、费用分摊、全屋规矩、住宿去留、一般噪音、
   电视音量、其它杂事——路由只会在清单 id、`none`、`reply_only` 里选，这类主题只能得到
   `none`，**零第三方出站**，这轮落回普通对话（不会被吞掉）。
2. **否定 / 条件捆绑 / 征询意见**：「先别提醒阿川……」「等他把地漏的头发清干净了，再提醒他」
   「要不要提醒阿川 / 我该不该跟他说」——这类表达**不构成明确交办、这一轮不该动作**，但
   主题**确实围绕某项已批准功能**，路由返回保留结果 `reply_only`。它**不是功能、不是工具**：
   走一条**无工具、无出站**的小回复（`reply-only.ts`），只跟当前说话人讨论 / 确认「这一轮
   不动作」，一两句，**不假装已经替他发了、不列能力清单、不记立场**。（判定由模型做，
   不靠穷举中文正则。）
3. **同时交办两个**：同一句话被明确交办了两件已批准功能 → **不猜**，路由返回 `reply_only`
   （围绕已批准功能但不是明确的一件），零出站，只回当前说话人一句。
4. **收件人不唯一**：没点名、泛指所有人、点名超过一位、点到自己——纯代码
   `resolveNamedRecipient` 直接不绑定，前门连判据都不启动（歧义时回一句澄清，零出站）。
   `reply_only` 同样只在收件人可绑定时才可能触发；绑不上就整轮落回普通对话。

**第二道：生成收窄 + 纯代码投递**（前门启动了，但走不到出站）：

- **夹带**：同一轮里夹带别的诉求（例如「深夜别开洗衣机，顺便把头发清了，水费也分摊一下，
  以后全屋都得守」）时，**生成阶段只拿本功能获准的有限字段**，夹带内容一个字节都没进它的
  输入，因此不可能写进正文，也不会被单独执行。
- **来源情境 / 第一人称**：抽取只保留枚举 / 布尔字段，**原始时间原话、空间细节（「机器挨着我
  房间那面墙」）、「我被吵醒」「我的东西」这类来源情境根本不进生成阶段**；提示词也要求
  第三人称中立口吻。这样 AI 不会把自己写成受影响的住户，也不会把住户的私人处境转述出去。
- **生成拿不出正文**：模型写不出可用正文（空）时，不形成出站，前门落回普通对话、零写入。
- **不可达**：收件人姓名未确认或当前渠道没有地址时，回给住户一句真话说明，`sms` 为 `null`、
  零写入。
- **发送硬闸**：任何落库写入都要过 `assertCanWrite`——本地进程写真实数据一律被拦。

## 旧 doctrine / 主生成大脑今天只兜住剩下的路径

功能前门把「替住户对别人做事」这条线整体从旧主生成里切了出来。**受控路径根本不读旧
doctrine，也不进主生成的工具循环**：

- **命中已批准功能**：路由命中后由**被选中那一个功能**抽取本功能获准字段、写正文，
  再由纯代码投递——这一轮 `toolsUsed` 为空、`promptComposition` 为 `null`，**旧
  doctrine（`lib/ai/brains/coliving/doctrine/*.md`）与主生成大脑完全没有被装配**。
- **统一产品功能问答**（`lib/chat/coliving/feature-qa.ts` + 事实源 `feature-facts.ts`，
  corpus-035 修法）：住户问「你有什么功能 / 能不能做 X / 为什么 X 不能做 / 刚才为什么
  拒绝」这类**功能边界元问题**时都**不进主生成**——入口读统一功能事实源，把**与问题
  有关**的事实（被拒事项 / 原因 / 当前开放功能名）交给模型说人话，再经**通用 grounding
  校验**：正文必须覆盖被选中条目的名称与理由锚点，问能力清单时必须列全
  `APPROVED_FEATURES`，漏项 / 说错 / 内部术语 / 超长一律用只含事实的兜底。
  它同样 `toolsUsed` 为空、`promptComposition` 为 `null`、**不读旧 doctrine**；上一轮
  同人的 `unsupported` 只用来把「刚才」关联到事实源条目，**不是**进入本路径的前提。
- **共享 grounding 闸**（`lib/chat/coliving/feature-grounding.ts`，corpus-035 第一轮实跑
  修法）：`unsupported` 与功能问答两条**无工具、无第三方出站**的路径共用同一条纯代码
  判定——正文里不得**承诺 AI 自己去联系 / 协调 / 跟进**（「我这就去跟他说」），也不得
  **把办不了的事推回住户**（「你可能得直接跟他说一下」「你自己找房东」「换个渠道」
  「以后再说」）。命中任何一条即以**只含代码事实**的中性兜底替换，绝不把这类越界正文
  发出去；这是**一条通用规则**，换未开放主题 / 换问法都不改。
- **只有这两条受控路径都没接住的请求**（不在清单里的主题、没点名收件人、普通聊天等）
  才落回**旧提示词大脑**——那时旧 doctrine 与主生成照旧装配、照旧约束这一轮。

因此**现在不要删掉整套 doctrine**：它仍是回退路径与大批普通对话的唯一约束，只是**它的
作用面随功能逐项开放而收缩**——每新增一项受约束功能，就有一类请求从「旧大脑自由发挥」
搬进「代码硬控 + 收窄字段生成」。删除时机是受控路径覆盖到旧路径再无可兜之事，而不是现在。

## 现在明确做不到的（住户能感知）

- **一般噪音 / 深夜噪音提醒（非洗衣）**：只能提醒「深夜别用洗衣机或烘干机」这一件；
  说话声、搬家具、电视音量等其它噪音仍不能替住户私下提醒。
- **卫生整改 / 清理头发**：不能替住户要求室友「洗完澡清掉浴室墙面与地漏里的头发」。
  现场程度的卫生整改**仍未开放**。
- **任何代转达、代问、催办、协调**：不能把住户的话替转给另一个住户。
- **群体联系 / 群发**：不能分别联系多个住户，也不能替一群人约谈某个人。
- **主动发起**：cron 的四类主动作业（回访、问全规则、接触新住户、到期提醒）全部停用；
  房东入库也不再收到第一条消息。住户不开口，AI 不主动发。
- 遇到上面这些请求，AI 只能在**跟当前说话人**的对话里回复，并如实说明这件事它没法
  替对方发出去；**不能用自由文本假装已经联系过对方**。住户**明确点名要 AI 联系某位
  室友办事、但主题不在已批准清单里**时，功能前门返回保留结果 `unsupported`（不是功能、
  不是工具），走 `unsupported.ts` 的**无工具、无第三方出站**小回复，只用一句真话说明
  没有发 / 目前没法替他发；住户本轮明确追问为什么时才简单说明处理不了，**不主动列能力
  清单**。普通主流程里，只要本轮**没有任何通过审稿的第三方出站**、回复却在声称已经 /
  正在联系某人（含**省略主语**的「已经跟阿杰说了」——029 真实事故），命中
  `claimsUnsentThirdPartyContact` 时那句话会被替换成一句说真话的未发送说明
  （只说「没发出去」，不列内部能力清单）；替换后**重新过一次确定性事实核对**，
  而不是只把 `replyReview` 标红却仍把假话发出去。
- **绝不主动列能力清单**：普通回复里不讲「我只能做 A、B 两件事」这类内部边界。
  运行时上下文（`context.ts`）**也不再预先宣传能力清单**——边界由代码硬控，不靠提示词。

## 机械检查证明什么、证明不了什么（新增功能必须走人工语言审阅）

**`pnpm coliving:quality` 里的断言只证明结构**：谁收到、有没有出站、**字段有没有被收窄**
（生成阶段的输入里没有夹带诉求）、正文是不是模型生成的那一句、收件人是不是代码绑定的
那位——这些是**地板，不是语言质量验收**。它**证明不了**这句话读起来是否自然、语气
是否得体、分寸是否合适。

因此：**每新增一个受约束出站功能，除了加确定性检查与结构闸，还必须走一遍
doctrine（`lib/ai/brains/coliving/doctrine/domain/relay.md`）对照 + 真实语料的逐轮
人工阅读**，必要时配 semantic judge。只让机械断言变绿就宣称「语气没问题」是不允许的
（老板 2026-09-13 明确：语气这一层机械测不了）。

## 为什么是这些、不是别的

老板 2026-09-12 选严格口径：立刻收回所有自由文本的第三方出站，只保留**程序化受约束**
的功能，并按「具体功能」逐项开放。老板 2026-09-13 把**能力面、功能、工具**三者分开：
边界（能替谁、发哪件事）由**代码写死的清单 + 一次内部白名单路由**硬控，**发出去的那
句话回到大模型写**，而**功能不是工具**——不往主生成的工具表里塞短信工具或功能工具，
因为那既白烧 token（每个功能一套 schema 与工具选择仪式），又让「能不能发」变成事后
把关而不是前门白名单。识别不是"每个功能各调一次判据"（清单长大等于每条消息 N 次
调用），而是**一次路由**：路由器只能在代码清单的 id、`none`、`reply_only`、`unsupported`
里选一个，命中的功能才被抽取本功能获准字段、写正文；围绕功能但本轮不动作的走
`reply_only`、点名要 AI 找室友办事但主题不在清单的走 `unsupported`（两者都无工具、无
第三方出站、只回当前说话人），真正无关的才 `none` 落回普通对话。**路由 / 抽取 / 生成
（含 reply_only / unsupported 小回复）的真实用量一律并进本轮台账**，未命中或失败也不丢。

卫生整改、一般噪音、代转达、群体联系、cron 主动发起等**仍然明确不开放**——不是被
遗忘，是要开放必须逐项走同一条评审，不能靠恢复通用工具或自由文案蒙混回来。

## 代码落点

## 以后要新增一项受约束功能的做法

1. **新起一个朴素模块**（照 `personal-item-reminder.ts` 的样子）：一句 `routeDescription`
   （给内部路由器看）、一个小抽取 schema（本功能获准字段，**不回答 match**）、一段小提示词、
   一个把收窄字段写成正文的 compose、一句兜底短句。**各功能各写各的代码，允许重复，
   不强行抽象。**
2. 在 `lib/chat/coliving/features.ts` 的 `APPROVED_FEATURES` 里把新功能**登记进代码清单**。
   清单是白名单，也是**路由器的枚举来源**：没登记的主题根本不会被选中，`none` / 同时
   交办两个都不执行。**路由仍然只调一次**——新增功能只让那一次路由多认一个 id，不会
   变成每个功能各调一次。
3. **沿用同一个投递服务**（`sms-delivery.ts`）——不要再加一个 LLM tool，不要把功能包装成
   action card / proposal / functionId 选择仪式，也不要在 `context.ts` 里预先宣传能力清单。
4. 更新本文件，并**按上面的「机械检查证明不了什么」走一遍 doctrine + 真实语料人工阅读**。
5. 加免费确定性检查（清单写死 / 收窄字段不泄漏 / 假 repo 行为 / mock 模型正文来源 / 零出站轮）
   + 一条隔离场景，再交 Codex 验收。

**不要**恢复 `contactPerson` 工具或 outreach 的自由文本生成——那是被明确收回的通用出口。
