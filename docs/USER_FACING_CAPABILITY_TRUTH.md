# 用户能力说明

> 这份文件只保存住户听得懂、真正需要知道的事实。不要写路由、模型、提示词、
> schema、数据库、工具、测试或其它内部实现。技术设计另见
> `docs/FEATURE_RUNTIME_ARCHITECTURE.md`。

## 现在有什么功能

### 个人物品使用提醒

- 能做什么：住户可以请 AI 提醒一位点名室友，使用自己的个人物品前先征得同意。
- 为什么开发：物品归谁、应不应该先问，边界比较明确；AI 不需要判断现场严重程度，
  也能把提醒说得中立、有理由。

### 夜间洗衣提醒

- 能做什么：住户可以请 AI 提醒一位点名室友，深夜避免使用洗衣机或烘干机影响别人休息。
- 为什么开发：深夜机器噪音影响休息是较明确、可以独立处理的共同影响，不需要先替任何一方
  判定复杂的是非。

## 现在为什么有些要求会被拒绝

### 卫生整改

- 目前不能做什么：AI 不能替住户要求室友清理地漏头发或完成其它卫生整改。
- 为什么暂不开发：AI 看不到现场程度，目前不能可靠判断是否已经达到需要要求别人整改的标准；
  不能只按照一个人的洁癖程度要求另一方执行。
- 用户追问时怎样解释：直接说明看不到现场程度、目前无法可靠判断，不讲内部技术过程，也不编造
  其它处理方案。

### 其它尚未批准的要求

- 如果没有记录具体原因，只能如实说这件事目前不在可替用户执行的范围内。
- 不得为了显得有解释而临时编一个“为什么不能做”。

## 以后怎样维护

老板批准一个新功能时，同时把老板给出的以下信息写进本文件：

1. 功能叫什么；
2. 用户可以让它做什么；
3. 为什么值得开发；
4. 必要时说明它不能顺带做什么。

老板明确暂不开发或拒绝一类功能时，记录：这类要求是什么、为什么暂不开发，以及用户追问时
可以如实说明的理由。老板没有给出理由时不替老板编理由，等开发依据明确后再补。

这项维护是每次功能批准、暂缓或边界改变时的默认收尾动作，不需要老板再次提醒。
