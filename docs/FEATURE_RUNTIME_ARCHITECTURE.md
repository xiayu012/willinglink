# 功能运行架构（内部技术说明）

> 用途：回答一个具体问题——**AI 现在到底能替住户对「别人」做什么。**
> 涉及第三方出站、代转达、主动联系人、cron 主动发起的改动，先读本文件。
> 建立于 2026-09-12 老板「具体功能逐项开放」严格口径。
> 同目录相关：`.claude/CONCRETE_FUNCTIONS.md`（具体功能总册）、`.claude/PROJECT_STATE.md`。

> **2026-09-13 定稿（本文件的当前口径）**：老板把三个层次分清楚了——
> **功能**是唯一正式的**最小批准单位、产品实现单位**（目前只有「个人物品使用提醒」
> 「夜间洗衣提醒」两件），像传统软件一样**各写各的朴素代码**，允许重复、不强行抽象；
> **工具只是底层机械动作**——**功能不是工具**。
>
> 同一天老板又定了**默认宽容**这一版边界：
>
> - **已批准功能清单不再是权限边界，而是一条低成本、稳定的优化快路径**。命中这两项时，
>   `turn.ts` 在 `buildContext` 之后、主生成之前走**功能前门**，用**一次内部白名单路由**
>   选中**恰好一个**功能，只抽取**本功能获准的有限结构字段**（枚举 / 布尔，不含来源情境）
>   交给模型写正文，再由**纯代码投递服务**（`sms-delivery.ts`）绑定原话点名且唯一的收件人
>   并落库——命中轮**不进主生成、不调任何工具**（`toolsUsed` 为空），更快、更省。
> - **清单外的请求不再因「不在清单里」被自动拒绝**：前门返回 `none` 时，这轮**落回
>   完整的 doctrine + 运行时主生成**。那里恢复了**通用短信联系能力**（`contactPerson`
>   工具，常驻主生成工具表）：**是否该替住户去联系某位同屋人，由 doctrine 情境准则 +
>   本轮 intent 判断**（协调者本来就可以按流程判断该不该联系），**不是**代码按关键词、
>   也**不是**新加一条「住户必须明说才准联系」的窄规则——那会把旧成熟设计里本来允许的
>   协调判断砍掉。**这不是回到自由文本出站**——落库仍走同一套收件人绑定、可达性、竞态
>   与 `assertCanWrite` 硬闸。
> - **真正办不了的事只有一个来源：显式黑名单**（`blacklist.ts` 的
>   `BLACKLISTED_CAPABILITIES`，**当前登记了唯一一项「单方面叫别人在洗完澡后清理地漏
>   头发」**：住户单方面交办 AI 去要求点名的一位室友，清理由其洗澡 / 使用浴室后留在地漏里的
>   头发）。**功能是精确行为、不是「一类主题」**（老板 2026-09-13 纠正）：条目名与稳定 id
>   都直接表达**这一个具体动作**、允许名字很长；**每一项各自拥有一个很小的纯代码资格复核**
>   （`qualifier`），精确优先于省代码。**它复用前门那一次功能路由**（条目以 `blocked:<id>`
>   token 摆给模型，只有模型判定住户**正在交办**该项时才进入），**路由选中后还要过该条目
>   自己的 `qualifier`**（地漏 + 头发 + 叫 / 让 / 请对方清理，缺一即当作 `none` 落回完整
>   流程），命中即由**纯代码**真话回复、零出站；**不按关键词、不加第二次 LLM 调用**。
>   **表里没有的事项、或经讨论 / 否定 / 引用 / 提问，都不拦**。登记原因如实保留：系统看不到
>   现场严重程度、当前技术还不能可靠判断"脏到什么程度才适合替一方要求另一方整改"；不是因为
>   问题不重要，也不是让住户自己处理。
> - **长期会再切回「清单外一律拒绝」**：等专门优化的功能覆盖足够、老板决定收紧时，
>   只要往 `BLACKLISTED_CAPABILITIES` / 路由里加东西即可；**现在不实现双模式死代码**。
>
> 路由器另有**保留结果 `reply_only`**：请求明确围绕某项功能，但这一轮是否定 / 征询 /
> 附条件、不能立即执行——它不是功能、不是工具，走一条**无工具、无出站**的小回复，只跟
> 当前说话人讨论「这一轮不动作」。**「同一句话里同时交办两件」不属于 `reply_only`**——
> 那要走 `none`、整条交给完整主流程（取一件丢掉另一件是错的）。不新增 LLM tool、
> 不做 action card / proposal / functionId 工具选择仪式、也不写死正文常量。
>
> 下面是这一版的口径；2026-09-12 的「纯正则 + 写死常量」、其后的「动作卡 / proposition」、
> 中间那版「唯一共享工具 `sendRoommateMessage`」、以及 2026-09-13 早先那版「白名单即权限
> 边界 + `unsupported` 保留轮」都是**已被驳回的历史**，不再描述当前行为。

> **历史术语归属（2026-09-13）**：`.claude/INTENT_CAPABILITY_ARCHITECTURE_V0.md`、
> `.claude/ONE_TO_ONE_RELAY_CAPABILITY.md`、`.claude/DOCTRINE_DEVELOPMENT_MAP.md`、
> `.claude/BRAIN_IMPROVEMENT_ROADMAP.md`、`.claude/AI_COST_ENGINEERING_REVIEW.md`，以及
> `.claude/AGENT_LOG.md` 与 `.claude/PROJECT_STATE.md` 里的历史条目中出现的旧集合层用语，
> 均为**历史用语，已由「功能」取代**，只作证据保留，**不得当作现行架构 / 批准 / 路线口径**，
> 也不得照此恢复企业微信、小红书私信、cron 主动发起或审稿重写等已收回的通道与路径。

  `scripts/wecom-selftest.ts` 删除，`wecom:selftest` 命令、`proxy.ts` 的 `/api/wecom`

  但**新的运行时不得再宣称或加载企业微信渠道**。

  `JIJYUN_WEBHOOK_URL`、私信模型 `XHS_DM_MODEL`、`CHANNELS` 里的 `xhs` 全部去掉。
- **小红书不是实时消息通道的部分保留不动**：房源来源（`/api/xhs/rental-ingest`、
  `xhsRental*` 表、标题/地理分类、房源清理脚本）与**帖子评论草稿**
  （`/api/xhs/comment-reply`）。评论草稿是替用户写一段评论文字，不接 webhook、

- 免费结构闸 `scripts/coliving-quality-inspect.ts` 守住这两条：`CHANNELS` 只有
  `web` / `sms`（不含 wecom、xhs）；企业微信的运行文件、`package.json` 自检命令、
  `proxy.ts` 路由与运行时代码里的 `wecom` 字面量均已清除；小红书私信的四条运行
  文件（`/api/xhs/messages` 路由、`xhs-dm.ts`、`jijyun.ts`、`redact-contact.ts`）
  不存在；同时确认小红书**房源采集**与**帖子评论草稿**路由仍在，以及 Twilio 短信
  投递与两项已批准功能（个人物品、夜间洗衣）仍可投递。

## 三种替住户对外行动的方式（按成本从低到高）

1. **专门优化的功能快路径**（`features.ts` 前门，命中 → 收窄字段生成 → 纯代码投递）。
2. **完整协调流程**（前门 `none` → doctrine + 主生成；由 doctrine 情境准则 + 本轮 intent
   判断是否该用常驻的 `contactPerson` 工具把话发给某位同屋人）。
3. **显式黑名单**（`blacklist.ts`，复用前门那一次路由的 `blocked:<id>` 选项）。老板明确
   登记为办不了的事项、且模型判定住户**正在交办**它、**并通过该条目自己的资格复核**时，
   纯代码回一句真话、零出站。**当前只有一项「单方面叫别人在洗完澡后清理地漏头发」**
   （要求点名室友清掉其洗澡后留在地漏里的头发）。

### 1. 已批准功能快路径（两项）

两项功能**各写各的朴素模块**，但共用**同一个功能前门**与**同一个纯代码投递服务**。

数据流（关键：**生成阶段看不到原始混合请求**）：

```
住户原话
  → 代码绑定收件人  resolveNamedRecipient（原话点名且唯一；不唯一/没点名/点自己 → 前门不启动）
  → 一次白名单路由   routeApprovedFeature（内部模型只从代码清单 id 里选一个、none、reply_only，
                     或显式黑名单条目的 blocked:<id> token）
                     （none → 落回完整协调流程：doctrine + 主生成；路由用量照计）
  → 命中功能 extract（只抽取本功能获准的有限结构字段）→ 模型写正文与短回执（compose；看不到原话、夹带诉求与来源情境）
  → 纯代码 deliverSms（可达性 + assertCanWrite 硬闸 → recordDecision → 入队 → 落库出站）
  → 或 reply_only    generateReplyOnlyReply（无工具、无出站，只回当前住户一两句；用量照计）
  → 或 blacklisted   blacklistedReply（纯代码真话、零出站；路由没选 blocked: 时不会出现）
```

1. 住户**明确交办**这两件事之一、并**点名**名册里恰好一位非本人同住人时，功能前门才启动。
   前置的收件人绑定是**纯代码**判定（`resolveNamedRecipient`：名册里名字被原话点名、且
   唯一、且不是发起人）——**不判断主题**，所以它不会替模型认主题。
2. **功能识别靠模型、不写穷举中文正则，但只调一次**：`features.ts` 发起**一次**内部
   白名单路由调用，路由器只能在 `APPROVED_FEATURES` 的 id 里选一个、`none`、保留结果
   `reply_only`，或某个显式黑名单条目的 `blocked:<id>` token（当前一项「单方面叫别人在
   洗完澡后清理地漏头发」）。
   它**不是
   LLM tool、不暴露给主 agent、不新增 tool schema**；命中后也只调**被选中那一个功能**的
   `extract` 抽取**本功能获准的有限结构字段**（设备类别 / 时段 / 是否影响休息；哪件物品 /
   用完有没有归位——**都是枚举或布尔，不收任意原文**）。路由用生产模型
   `deepseek/deepseek-v4.1-flash`，temperature 0。**清单写死在代码里**，命中哪一项由代码
   精确比对。这样清单里加到 20 项，一条消息也仍然只多一次路由调用，而不是 20 次。
   **只有整条交办恰好完整落在同一个功能里才选它**；同一句话夹带了别的需要执行的诉求
   （另一件已批准功能，或任何清单外请求）就返回 `none`、整条交给完整主流程。
3. **正文由模型写**（不是写死常量、不要求按命令说话、不做二次确认）：生成阶段只拿到
   **收窄后的有限字段**——它看不到原始混合请求、看不到夹带的其它诉求、也看不到来源情境
   （谁提出来的、是谁被打扰、原话里的时间或空间细节）。因此模型不可能把这些写进正文。
   提示词明确要求**第三人称、中立的协调员口吻**：AI 是替这栋房子传话的协调员，不是受影响
   的住户，绝不能写「我被吵醒」「我房间」「我的东西」；也**不得凭空断言当前时间 /「今晚」/
   「已经发生」**——时段字段只表示"希望对方避开"，不代表"现在就是那个时段"。正文短、
   自然、有理由、说清请对方怎么做；短回执也由模型写，为空时才回落到本功能的兜底短句。
4. 纯代码投递服务 `deliverSms` 在发送前最后核一遍：收件人必须是原话点名且唯一的那位
   （模型改不了人）；**可达性**（姓名已确认、当前渠道有地址）不满足就回一句真话、零写入；
   落任何写入都过 `assertCanWrite` 发送硬闸。

#### 1. 个人物品使用提醒

- 主题：**用我的个人物品前先问我。**
- 触发（自然语言即可）：住户点名一位室友、明确要 AI 去提醒、说的正好是这一件事。
  典型：「阿川昨天没跟我说一声就拿了我放在客厅的充电器用，用完也没放回去。你帮我
  跟他说一下，以后要用我的东西先问我。」旧窄命令形态（「提醒 阿川：使用我的个人物品
  前先问我」）仍然可用，但**不再是唯一入口**。
- 发给对方的正文由模型写，例如「阿川，室友的个人物品他有时候自己也要用，你用之前先
  跟他说一声，方便他安排，谢谢。」——**第三人称、中立协调员口吻、有理由、有具体请求**，
  不是冷命令；也**不会用第一人称冒充物品主人**（不提「我的东西」「我搁在」，也不点名
  是谁提出来的）。
- 判据模块：`lib/chat/coliving/personal-item-reminder.ts`。

#### 2. 夜间洗衣提醒

- 主题：**深夜别用洗衣机或烘干机。**
- 触发（自然语言即可）：住户点名一位室友、明确要 AI 去提醒、说的正好是这一件事。
  典型：「阿川昨天凌晨四点开洗衣机和烘干机，机器就挨着我房间那面墙，我被吵醒了。
  你能不能私下跟他讲一下，这一次先别在深夜洗和烘干。」
- 发给对方的正文由模型写，例如「阿川，深夜开洗衣机或烘干机的声音会吵到休息，麻烦你
  尽量避开深夜时段，谢谢。」
- 只处理「深夜运行洗衣机 / 烘干机影响别人休息」这一件共同影响，**不要求 AI 先裁定
  谁的卫生阈值或物品所有权**；不能从它外推到一般噪音、一般清洁、规则制定、费用或
  去留协调。**电视音量（corpus-029）不属于这两件事**：路由返回 none，功能前门不执行，
  这轮**落回完整协调流程**——住户明确要求联系阿杰时，主生成会用 `contactPerson`
  把话真的发给他（不是模板、不是假装）。
- 判据模块：`lib/chat/coliving/night-laundry-reminder.ts`。

### 2. 完整协调流程（默认宽容后的回退路径）

前门返回 `none` 时（主题不在专门优化清单里、没点名唯一收件人、普通聊天等），
`turn.ts` 照旧装配 **doctrine + 运行时上下文**并进入**主生成**。主生成的工具表里
**恢复了常驻的 `contactPerson` 工具**：

- **是否该替住户去联系某人，由 doctrine 情境准则 + 本轮 intent 判断**（协调者本来就可以
  按流程判断该不该联系）；调 `contactPerson` 时，主生成真的把一句第三人称、中立的提醒
  发给对方。**代码不在这里按关键词分叉**，也**不加**「住户必须明说才准联系」这类新窄规则
  ——那是把旧成熟设计里本来允许的协调判断砍掉。
- `contactPerson` 的执行仍是**代码硬控**：名字必须能在名册里唯一定位（`findPersonByName`）、
  不能联系发起人自己、同一轮同一人只发一次（`contacted` 去重）、若目标已有本人未结的
  沟通则不重复发（`findRecentOpenCommunication`）、发送前过**竞态门禁**
  （`hasNewInboundSince`，有更新的入站就把这条标 `skipped`）、**排班一致性硬闸**
  （`scheduleWindowLabel` / `scheduleSlot` 与 `checkScheduleSlotConsistency` 对齐，
  不一致就零出站）、落库过 `assertCanWrite`，并同时写 communication 与对方会话。
- **来源隐私闸（纯代码，默认匿名）**：真正入队前过 `checkSourcePrivacy`（`turn.ts`）——
  正文**不得出现发信人姓名**、**不得把请求归因给来源人**（「他想请你…」「她说让你…」
  「有人反映…」）、也**不得转述来源人的私人处境**（高精度枚举的睡眠状态：`失眠 / 没合眼 /
  没睡好 / 没睡着 / 补觉 / 睡不着` 等）；命中就拒绝这次发送、让同一轮模型改成中立说法，
  **不进 `contacted` / `outbound`、不落库**（在它有副作用之前拦）。**目标收件人本人的姓名
  允许出现**（短信本来就要称呼他）；`声音大 / 影响别人休息 / 夜里容易影响休息` 这类**共享
  可观察的必要理由必须放行**。**恢复通用联系 ≠ 恢复来源泄露**：当前没有「来源人明确同意
  暴露」的例外，一律匿名更安全。起因是 029 模型验收抓到的真实出站泄露（先同时出现来源姓名、
  来源人私人状况「补觉/睡不着」与归因句「她想请你」；清掉姓名与归因句后仍转述私人处境
  「有人补觉、睡不着」），generation-only 下无 critic，靠这条纯代码闸兜底。确定性闸只收**能
  高精度枚举**的睡眠状态，**不假装覆盖所有语义隐私**（健康 / 财务 / 去向 / 情绪 / 动机等更宽
  的面仍靠 doctrine 约束）。
- **行为与决定一致**：调 `contactPerson` 时主生成填的联系决定 `kind` 必须是
  `contact_one`（联系多人 `contact_group`），不能嘴上说联系、决定却是别的。
- **不恢复**企业微信、小红书私信、cron 主动发起 / outreach、LLM 批判器与重写。
  生产仍是**只生成**（`outreach.ts` 入口返回空）。

### 3. 显式黑名单（当前一项：单方面叫别人在洗完澡后清理地漏头发）

- `lib/chat/coliving/blacklist.ts` 是**唯一**「这件事办不了」的事实源：老板明确登记为
  办不了的事项才写进 `BLACKLISTED_CAPABILITIES`。每条含 id / label / reason /
  `routeDescription` / keywords / **`qualifier`（该条目自己的纯代码资格复核）** / 验证锚点。
- **老板 2026-09-13 纠正：功能是精确行为、不是「一类主题」。** 上一版把这条命名为宽泛的
  「卫生整改要求」（`hygiene-rectification`），把"要求某位室友整改卫生"整类包进来，范围过宽。
  现在 id 与 label 都直接表达**这一个具体动作**，名字允许很长；**以后白名单 / 黑名单里每
  一项都遵循这个粒度**，不为省代码把相邻行为包成一个主题类别。
- **当前唯一条目「单方面叫别人在洗完澡后清理地漏头发」**
  （`id: ask-named-roommate-clean-shower-drain-hair`）：住户单方面交办 AI 去要求**点名的一位
  室友**，清理由其洗澡 / 使用浴室后留在**地漏里的头发**。理由如实保留：**系统看不到地漏头发 /
  卫生现场的严重程度；即使用户描述了现场，当前技术也还没开发到能可靠判断"脏到什么程度才适合
  替一方要求另一方整改"的水平**。它不是"问题不重要"，也不是"让住户自己处理"。
- **严格限于这一个具体动作，不得扩大**：浴室**墙面**头发、地漏**维修 / 疏通**（没要求清理
  头发）、一般打扫卫生、污渍、只说某处有异味 / 想开窗通风、讨论清洁怎么安排、普通抱怨 /
  问看法 / 提醒 / 费用 / 规矩 / 去留 / 一般噪音都**不是这一项**，它们照旧返回 `none`、
  落回完整协调流程（corpus-036 的宿舍异味 → `contactPerson` 联系阿杰就是这种相邻情形，
  不得被这条拦下）。
- **阻断复用前门那一次路由，不按关键词、不加第二次 LLM 调用**：条目以 `blocked:<id>`
  token 作为那次路由的**可选项**摆给模型，代码用 `blacklistedCapabilityByRouteToken`
  精确解析；**只有模型判定住户正在交办该项**时才进入（只是讨论 / 否定 / 引用 / 问为什么
  都不选它）。
- **路由选中后还有一道该条目自己的纯代码资格复核**（`qualifier`，见 `features.ts` 的
  `runApprovedFeature`）：原话必须同时具备本功能的必要信号（**地漏 + 头发 + 叫 / 让 / 请
  对方清理**；点名收件人已由前门 `resolveNamedRecipient` 保证）。不通过就当作 `none` 落回
  完整流程——**精确优先于省代码，宁可漏判，不得误杀相邻行为**。这样即使模型把相邻主题误选成
  `blocked:<id>`，代码也不会替它把相邻行为拦下。
- 复核通过才回一句 `blacklistedReply`（只含登记的真话与原因），**零出站、不进主生成**。
  `keywords` **只供产品功能问答**（`feature-facts.ts` 的 `selectBlacklistedCapabilities`）
  把问题关联到条目做解释，**不做执行阻断**，且与 `qualifier` 一起收窄以免把相邻主题的问题
  也说成"办不了"。
- **表里没有的事项恒不命中**；以后长期要切回「清单外一律拒绝」时，也是往这张表 / 路由里
  加东西，而不是现在写死复杂的分支。
- **当前适用面（不要假装更宽）**：这条阻断接在功能前门里，而前门只在**原话点名了唯一一位
  同住人**时才启动——所以现在的黑名单定义面是**「对点名的同住人执行某个功能」这一类**
  请求（和两条已批准快路径同一类）。要覆盖别的形态得先扩展前门。

### 4. 共同规则协商（默认关闭的实验接线，只处理一条具体规则）

**这一条与上面第 3 条的黑名单不是同一件事，必须分清**（见 `.claude/CONCRETE_FUNCTIONS.md`
与 `docs/USER_FACING_CAPABILITY_TRUTH.md`）：

- 黑名单「单方面叫别人在洗完澡后清理地漏头发」= 一位住户**单方面**交办 AI 去要求**点名
  的一位室友**清理；**精确不变**。
- 共同规则协商 = **全屋住户一起**把「每个人洗完澡后都把地漏里的头发清掉」定成一条**对每个
  人都适用**的规则，**全员同意才生效**。它不是「谁要求谁」，不需要判断现场严重程度，因此
  **不属于**那条黑名单，也不得被它拦下；反过来它也**不得**替单方面整改放行。

**状态机（纯函数，零耦合）**：`lib/coordination/rule-consultation.ts`。只做「收集全员表态」
这一件事，不算方案、不判断规则内容是否合理、**不自己发明规则、不做任何现场卫生判断**。
事件 / 状态 / 不变量见 `lib/coordination/README.md` 的「第二条机器」一节。关键保证（全部由
代码强制，不靠模型自觉）：

- **未全员同意绝不定案**：`rule_settled` 生成时，日志里所有已知参与者必须都是 agree；
- **同意过 / 已征询过的人不重复征询**；
- **有人明确反对则原规则永不定案**（`objected` 终态，其余人同意也不翻转）；
- **来源隐私由类型保证**：投影 / 出站动作里没有 `initiator` 字段，措辞层拿不到是谁发起的；
- **不写死短信文案、不自己发送**：状态机只产出结构化动作（consult / announce），正文交给
  措辞层按 doctrine 生成；
- **身份一律用 `personId`**：参与者 / 发起人 / 收件人都按稳定 id，显示名只用于文案；收件人由
  `resolveRuleActionRecipients` **按 id** 解析。两位**同名**住户各有各的 id，会分别征询 /
  宣布，不会合并、也不会互相串收；
- **规则事实是中性固定语义**：写进状态机与措辞层的规则文本恒为
  `SHARED_SHOWER_DRAIN_HAIR_RULE_FACT`（「每个人洗完澡后清理地漏里的头发」），**不是**发起人
  原句片段——原句里的姓名 / 指责 / 私人理由都不会外传。最终短信措辞仍由措辞层自然生成，不写死
  完整短信；
- **事实与送达回执分开（回执必须等于真的送达）**：`rule_proposed` / `position_recorded` /
  `rule_settled` 是**事实**，推进时立即落库；`consulted` / `announced` 是**动作成功的回执**，
  只在对应短信（或本人回复）确实落账后由 `deliverRuleActions` / `recordRuleReceipt` 追加。
  发送失败**不记回执**，失败者留在待办里、下次问进度（`ask_status`）重新征询 / 补发；
- **推进之后绝不回落旧主流程**：`turn.ts` 的 `maybeSharedRuleReply` 只有在「确认属于本路径
  之前」（读名册失败 / 状态机推进抛错 / 不是这条规则）才返回 `null` 交回旧流程；一旦事实已
  推进，后续任何异常都返回一个「零出站、中性兜底」的安全结果，避免同一条入站消息被处理两次。

**接线（默认关闭）**：`lib/chat/coliving/rule-consultation-session.ts` 是唯一可测试运行路径
——一个**窄识别器**只认这**一条**具体规则（必须同时出现「全屋 / 每个人」范围信号 + 「定规则 /
约定」框架信号 + 「洗澡」「地漏」「头发」且同一分句里有清走动作），**不把"卫生 / 地漏 / 头发"
扩大成一类主题**，单方面点名要求**不进入**本路径（仍走原黑名单）。命中后才用
`parseOpenRuleSessionIntent`（不同意优先于同意；仅短回复或含规则字眼时才当表态，防劫持）解析
表态，按 household 落 JSONL 事件日志，再由 `advanceRuleConsultationSession` 推进状态机。

`turn.ts` 里的接线由环境变量 **`COLIVING_COORDINATION_SHARED_RULE=1`** 控制，**默认关闭**，
且仅在住户明确要求时才开启；开启后也**必须先过 doctrine + 真实语料人工阅读**才算语气验收
（见下节「机械检查证明不了什么」）。未开启时这条路径完全不参与，行为与现在一致。措辞层
`lib/chat/coliving/rule-consultation-notice.ts` 只拿到规则事实文本，**看不到发起人 / 投诉人 /
任何私人处境**；生成失败时回退到一句中性的「收到，我记下了。」，**绝不用兜底文案假称规则已经
生效**。另有纯代码的 `claimsSharedRuleSettled` 闸：未定案那一轮，住户回复里若出现「已经生效 /
定案 / 全员同意」这类措辞会被降级，避免假完成。

## 保留轮 `reply_only` 与两道保护

**保留结果 `reply_only`（不是功能、不是工具）**：请求明确围绕某项已批准功能，但这一轮
**否定 / 征询 / 附条件**、不能立即执行时，路由返回 `reply_only`，走
`reply-only.ts` 的**无工具、无出站**小回复，只回当前说话人一两句，**不假装已经替他发了、
不列能力清单、不记立场**。判定由模型做，不靠穷举中文正则。

**第一道：功能前门**（代码清单 + 一次白名单路由，命中才执行；其余落回完整协调流程）：

1. **不在清单上的主题**：费用分摊、全屋规矩、住宿去留、一般噪音、电视音量、说某处有异味、
   讨论清洁安排、其它杂事——路由只会在清单 id、`none`、`reply_only`、`blocked:` 里选，这类
   主题得到 `none`，前门**零第三方出站**，这轮**落回完整协调流程**（不会被吞掉，也不会被
   自动拒绝）。**「单方面叫别人在洗完澡后清理地漏头发」是唯一的例外**：住户点名室友、要 AI
   去要求对方清掉其洗澡后留在地漏里的头发时，路由选
   `blocked:ask-named-roommate-clean-shower-drain-hair`、再过该条目的 `qualifier`，纯代码
   真话回复、零出站（见上一节）。
2. **否定 / 条件捆绑 / 征询意见**：「先别提醒阿川……」「等他把地漏的头发清干净了，再提醒他」
   「要不要提醒阿川 / 我该不该跟他说」——主题**确实围绕某项已批准功能**，路由返回
   `reply_only`，无工具、无出站。
3. **一句里同时交办两件**：同一句话里夹带了另一项**需要执行**的诉求（另一件已批准功能，
   或任何清单外请求）→ **不猜、不截取**，路由返回 `none`，**整条交给完整主流程**——
   取一件、丢掉另一件是错的，`reply_only` 又会让整条都不执行。
4. **收件人不唯一**：没点名、泛指所有人、点名超过一位、点到自己——纯代码
   `resolveNamedRecipient` 直接不绑定，前门连判据都不启动。`reply_only` 同样只在收件人
   可绑定时才可能触发；绑不上就整轮落回完整协调流程。

**第二道：生成收窄 + 纯代码投递**（快路径启动了，但走不到出站）：

- **来源情境 / 第一人称**：抽取只保留枚举 / 布尔字段，**原始时间原话、空间细节（「机器挨着我
  房间那面墙」）、「我被吵醒」「我的东西」这类来源情境根本不进生成阶段**；提示词也要求
  第三人称中立口吻。这样 AI 不会把自己写成受影响的住户，也不会把住户的私人处境转述出去。
  （**夹带别的诉求的混合句不再走这里**——见第一道第 3 条，它整条落回完整主流程。）
- **生成拿不出正文**：模型写不出可用正文（空）时，不形成出站，前门落回完整协调流程、零写入。
- **不可达**：收件人姓名未确认或当前渠道没有地址时，回给住户一句真话说明，`sms` 为 `null`、
  零写入。
- **发送硬闸**：任何落库写入都要过 `assertCanWrite`——本地进程写真实数据一律被拦。

## 旧 doctrine 仍然保留，而且默认宽容下它的作用面更大（不要删）

功能前门只把**两条专门优化的快路径**从旧主生成里切了出来；受控路径不读旧 doctrine、也不进
主生成的工具循环——命中已批准功能那一轮 `toolsUsed` 为空、`promptComposition` 为 `null`，
**旧 doctrine（`lib/ai/brains/coliving/doctrine/*.md`）与主生成大脑完全没有被装配**。

但**默认宽容把作用面反过来了**：`none` 不再等于拒绝，所有清单外请求、绝大多数普通对话
都落回 **doctrine + 主生成**，其中就包括恢复的通用短信联系能力 `contactPerson`。所以
**现在更不能删整套 doctrine**——它正是这条回退路径（也是普通对话）的唯一约束；每新增一项
专门优化的快路径功能，只是把那一类请求从"旧大脑判断"搬进"窄上下文 + 收窄字段生成"，
剩下的仍然归它管。删除时机是快路径覆盖到旧路径再无可兜之事，而不是现在。

## 统一产品功能问答（`feature-qa.ts` + 事实源 `feature-facts.ts`）

住户问「你有什么功能 / 能不能做 X / 为什么 X 不能做 / 刚才为什么拒绝」这类**功能边界元
问题**时，**不进主生成**：入口读统一功能事实源，把**与问题有关**的事实交给模型说人话，
再经**通用 grounding 校验**。

- **口径不再是「只有两项功能」**：两项已批准功能是**专门优化的快路径**（更快、更省），
  不是全部能力；其它需要协调同住人的请求会走**完整的协调流程**处理，**不是不能做**。
- **不编造「办不了」**：只有黑名单里明确登记、且**与当前问题对得上、或由本人紧接被拒的
  结构化引用指名**的事项才说办不了，并保留登记的原因。没有任何可用条目时**不得**产生
  任何「办不了」的说法，也不得为它编造原因。
- **「刚才为什么」用一条窄结构化引用**：黑名单收口那一轮由**纯代码**把
  `{ blacklistedCapabilityId, personId }` 写进 decision payload；问答只按**本人 +
  紧接本人上一条入站 + 72h** 读回（`repo.latestBlacklistReference`），问题本身对不上
  条目时补上那一条——因而**同一住户紧接被拒的追问必须说出名称与登记原因**。本人后来
  发过别的、或别的住户发问（查询按 personId 收窄）都不会错误继承；**不读自由文本、
  不按关键词猜「刚才」**。
- 正文必须覆盖被选中黑名单条目的名称与理由锚点；问能力清单时必须列全
  `APPROVED_FEATURES`，漏项 / 说错 / 内部术语 / 超长一律用只含事实的代码兜底。
- 它同样 `toolsUsed` 为空、`promptComposition` 为 `null`、**不读旧 doctrine**、零第三方出站。

## 共享 grounding 闸（纯代码）

`lib/chat/coliving/feature-grounding.ts`（`findGroundingViolations`）：`reply-only.ts` 与
`feature-qa.ts` 两条**无工具、无第三方出站**的路径共用同一条纯代码判定——正文里不得
**承诺 AI 自己去联系 / 协调 / 跟进**（「我这就去跟他说」），也不得**把事推回住户**
（「你可能得直接跟他说一下」「你自己找房东」「换个渠道」「以后再说」）。命中任何一条即以
**只含代码事实**的中性兜底替换，绝不把这类越界正文发出去；这是**一条通用规则**，
换主题 / 换问法都不改。

## 假完成保护（主生成路径）

主生成若在**本轮没有任何通过确定性出站闸**（generation-only 下保留的那道代码闸）的第三方
出站的情况下，回复却声称已经 / 正在联系某人（含**省略主语**的「已经跟阿杰说了」——029
真实事故），命中 `claimsUnsentThirdPartyContact` 时那句话会被替换成一句说真话的未发送
说明（只说「没发出去」，不列内部能力清单）；替换后**重新过一次确定性事实核对**。反过来，
本轮**确实有**已接受的第三方出站时，**不得**把正常回执误替换。判定只看结构事实
（有没有真的发出去），不看模型口气。

## 机械检查证明什么、证明不了什么（新增功能必须走人工语言审阅）

**`pnpm coliving:quality` 里的断言只证明结构**：谁收到、有没有出站、**字段有没有被收窄**
（生成阶段的输入里没有夹带诉求）、正文是不是模型生成的那一句、收件人是不是代码绑定的
那位——这些是**地板，不是语言质量验收**。它**证明不了**这句话读起来是否自然、语气
是否得体、分寸是否合适。

因此：**每新增一个受约束出站功能，除了加确定性检查与结构闸，还必须走一遍
doctrine（`lib/ai/brains/coliving/doctrine/domain/relay.md`）对照 + 真实语料的逐轮
人工阅读**，必要时配 semantic judge。只让机械断言变绿就宣称「语气没问题」是不允许的
（老板 2026-09-13 明确：语气这一层机械测不了）。

## 为什么是这些、不是别的

老板 2026-09-12 先选严格口径：立刻收回所有自由文本的第三方出站，只保留**程序化受约束**
的功能，并按「具体功能」逐项开放。老板 2026-09-13 把**能力面、功能、工具**三者分开：
**功能不是工具**——不往主生成的工具表里塞功能工具，因为那既白烧 token（每个功能一套
schema 与工具选择仪式），又让「能不能发」变成事后把关。识别不是"每个功能各调一次判据"
（清单长大等于每条消息 N 次调用），而是**一次路由**。

**同一天老板又把默认口径改成宽容**：专门优化的两项继续走窄上下文快路径；**清单外不再
自动拒绝**，落回完整的、带 doctrine 的主生成，那里恢复了**通用短信联系能力**——是否该替
住户联系某位同屋人，由 doctrine + 本轮 intent 判断，AI 可以真的替他把话发出去。
**真正办不了的只有老板明确登记的黑名单**（当前一项：单方面叫别人在洗完澡后清理地漏头发）。
长远会再切回
「清单外一律拒绝」，但那是**改数据 / 改路由**的事，现在不写双模式死代码。

企业微信、小红书私信、cron 主动发起、LLM 批判器 / 重写等**仍然不恢复**——它们不是被
遗忘，是要恢复必须单独立项评审。

## 代码落点

- **功能清单与一次白名单路由（清单纯代码，路由一次模型调用）**：`lib/chat/coliving/features.ts`
  （`APPROVED_FEATURES` 写死已批准功能；`routeApprovedFeature` **一次**调用，只能在清单
  id、`none`、`reply_only`、黑名单 `blocked:<id>` 里选一个，不是 LLM tool、不新增 tool
  schema；`runApprovedFeature` 是唯一编排入口：路由 → 命中才抽取 → 执行（返回

## 以后要新增一项受约束功能的做法

1. **新起一个朴素模块**（照 `personal-item-reminder.ts` 的样子）：一句 `routeDescription`
   （给内部路由器看）、一个小抽取 schema（本功能获准字段，**不回答 match**）、一段小提示词、
   一个把收窄字段写成正文的 compose、一句兜底短句。**各功能各写各的代码，允许重复，
   不强行抽象。**
2. 在 `lib/chat/coliving/features.ts` 的 `APPROVED_FEATURES` 里把新功能**登记进代码清单**。
   清单是**路由器的枚举来源**：没登记的主题拿 `none`，这轮落回完整协调流程（默认宽容下
   **不是拒绝**）。**路由仍然只调一次**——新增功能只让那一次路由多认一个 id。
3. **沿用同一个投递服务**（`sms-delivery.ts`）——不要再加一个 LLM tool，不要把功能包装成
   action card / proposal / functionId 选择仪式，也不要在 `context.ts` 里预先宣传能力清单。
4. 更新本文件，并**按上面的「机械检查证明不了什么」走一遍 doctrine + 真实语料人工阅读**。
5. 加免费确定性检查（清单写死 / 收窄字段不泄漏 / 假 repo 行为 / mock 模型正文来源 / 零出站轮）
   + 一条隔离场景，再交 Codex 验收。

**默认宽容下不要再新建「清单外 = 拒绝」的路径**：真正办不了的事项由老板登记进
`blacklist.ts`，而不是靠路由默认拒绝。**不要**恢复企业微信、小红书私信、cron 主动发起
或 LLM 批判 / 重写。
