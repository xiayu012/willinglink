# WillingLink 协调大脑纠正账本

> 建立日期：2026-09-09
> 用途：把老板纠正、真实事故和开发反思沉淀成可检索证据。这里记录问题，不自动授权改产品。
> 维护原则：同类问题追加证据，不急着新增一条提示词；先判断它属于世界理解、判断、行动、表达还是验收。

## 怎么使用

每次出现新纠正，先回答五件事：

1. 用户实际看见了什么？
2. 理想结果是什么？
3. 错在输入理解、状态组织、判断、工具行动、表达，还是验收？
4. 过去是否出现过同类问题？已有修法是否真正覆盖？
5. 它应进入成功轨迹、确定性机制、提示词原则、升级边界，还是暂不处理？

不要把“模型这次说错了”直接翻译成“再加一句不要这样说”。

---

## 老板定义的三条一级红线（2026-09-09）

1. **推断性隐私泄露**：不要对 B 说出 A 很不希望 AI 说漏嘴的信息；即使不点名，B 能从细节推断出 A 或敏感事实也算泄露。
2. **能力不足却硬处理**：当前开发阶段，处理不来、历史上处理效果往往很差的事情，要直接告诉用户具体处理不了的部分，并完成安全交接。
3. **失去中立与稳定承托**：要中立；好的管理像坚实的大地，不站队、不漂移、不把决定责任推回住户。

这三条高于下面的普通纠正簇。详细能力分区见 `.claude/CAPABILITY_BOUNDARY_V0.md`。

## 首批纠正簇

### C01 · 对话对象与角色错位

- **用户看到的结果**：多人对白转化后，角色对协调 AI 说出“你自己的毛巾是红的”一类本应对另一住客说的话。
- **理想结果**：每句话必须保持原场景的说话人、收话人、被谈论对象和各自已知事实；不能只把人名替换成项目角色。
- **初步归层**：语料制作的世界模型错误；也提示运行时需要清晰的 `speaker / addressee / subject`。
- **已有处理**：这批纯对白以后由 Codex 直接转化；最近五条已复核对象关系。
- **仍需验证**：运行时是否也会把“住客转述另一人的话”误当成对 AI 的直接指令。
- **候选资产**：Golden Trace 的输入侧反例；现场卡的参与者关系字段。

### C02 · 翻译腔、客服腔与固定口头禅

- **用户看到的结果**：“有没有什么不顺手的”“有什么需要帮忙的吗”等中文不自然，而且提示词里的示例容易变成复读口头禅。
- **理想结果**：像现实中的中文协调者说话，随语境自然变化，不展示客服脚本痕迹。
- **初步归层**：表达；示例写法污染生成，而非业务流程缺失。
- **已有处理**：删除逐字话术，改写成意图描述；增加避免固定句式的原则。
- **风险**：继续用“禁用词清单”会无限增长，新口头禅仍会冒出来。
- **候选资产**：多样化成功回复；写话层单独验收。

### C03 · 身份概念混淆：房东不等于管理员

- **用户看到的结果**：把房东角色写成 manager，混淆房东、项目 AI 协调员和现实管理者。
- **理想结果**：产权/合同权限属于房东；日常协调角色属于 AI 协调员；两者不能因英文标签相近而互换。
- **初步归层**：实体与权限模型。
- **已有处理**：术语、角色字段和兼容路径曾统一整改。
- **仍需验证**：Golden Trace 中是否始终按权限而不是名称决定动作。
- **候选资产**：角色权限表；现场卡的角色与权限字段。

### C04 · 该拿主意时反复咨询用户

- **用户看到的结果**：厨房冲突等日常问题问很多轮，把相差很大的选项交给住户选择；不像“坚实的大地”。
- **理想结果**：只问会实质改变处理的缺项；流程、轻重和默认方案由协调系统承担，个人偏好留给当事人表达。
- **初步归层**：决策权分配 + 信息充分度判断。
- **已有处理**：doctrine 写入决定权归属、提问预算和“信息齐就推进”。
- **风险**：现有条款彼此冲突，模型可能同时学到“不要问”和“必须问诉求”。
- **候选资产**：完整与不完整信息各一组成功轨迹；本轮现场卡明确 `missing_decision_relevant_facts`。

### C05 · 公平数字成立，但生活结果荒谬

- **用户看到的结果**：厨房份额看似分清，却让人长期到 20:00 后才能做饭；或长占用者仍占据最有利时段。
- **理想结果**：不仅数学份额合理，还要考虑吃饭、睡眠、工作等现实后果；不能把被投诉的现状当分配起点。
- **初步归层**：组合优化能力 + 人类可接受性判断。
- **已有处理**：组合排列交给 `pickSchedule`，并增加结果合理性复核。
- **已知局限**：算法候选只能优化被明确表达的偏好；输入错、偏好漏记或目标函数选错，结果仍可能荒谬。
- **候选资产**：算法候选 + 人类判断的成套 Golden Trace；黄色升级条件。

### C06 · 机制聪明过头，脱离真实生活

- **用户看到的结果**：提出按周轮换做饭顺序等理论上公平、现实中难维护的制度，沉浸在自己的机制里。
- **理想结果**：优先使用人看一眼就能执行、不依赖持续监督和复杂记忆的安排。
- **初步归层**：方案复杂度偏好；缺少“执行摩擦”这一评价维度。
- **已有处理**：doctrine 已强调最小摩擦和不依赖监督。
- **仍需验证**：模型是否会在新领域换一种形式继续过度设计。
- **候选资产**：简单方案胜过复杂方案的成对示例；验收中的执行摩擦指标。

### C07 · 把发现问题的人变成承担成本的人

- **用户看到的结果**：厕所脏了，系统让最先发现的人承担清洁；或把共用提醒写成冲某个人的命令。
- **理想结果**：不能因为谁先开口就把责任落给谁；未知责任时按共用机制处理，已知造成者时由造成者承担。
- **初步归层**：因果归属 + 收件人角色判断。
- **已有处理**：critic 增加收件人角色；全屋规则和个体指令分开。
- **风险**：默认角色推断曾经修过头，说明不能只靠一个粗标签。
- **候选资产**：报告者、被说到者、共同使用者三视角 Golden Trace。

### C08 · 把“共用”擅自扩大成“全屋共用”

- **用户看到的结果**：系统因为设施或物品被描述为共用，就默认整栋房所有人都参与。
- **理想结果**：共用范围必须来自已知成员与场景事实；不知道就保留未知，不能用词义替代事实。
- **初步归层**：作用域与参与者识别。
- **已有处理**：曾回撤过度强调“共用”的提示词修法。
- **候选资产**：现场卡中的 `affected_people / sharing_scope / unknown_scope`；事实保真检查。

### C09 · 说会行动，但行动没有发生

- **用户看到的结果**：回复“我会去联系”“晚点告诉你”，实际没有联系、没有提醒，案件停住。
- **理想结果**：已联系、等待回复、已同意必须分开；本轮承诺的可控动作本轮执行，延后事项必须可追踪。
- **初步归层**：行动完成度和状态机，不是文风问题。
- **已有处理**：工具完成度校验、重写路径开放联系工具、延后承诺登记提醒。
- **已知教训**：只把空头承诺改成将来时，仍然没有解决用户的事。
- **候选资产**：组合工具；动作收据；未完成即升级或明确失败。

### C10 · 工具和规则变多后，原有流程被挤掉

- **用户看到的结果**：新增工具后，“添加住客立即打招呼”这一原本能走通的流程消失。
- **理想结果**：关键动作不能依赖模型在长工具列表里自己记得；系统扩展不应随机破坏旧流程。
- **初步归层**：手脚编排与注意力负载。
- **已有处理**：该个案加了代码级完成度校验。
- **战略意义**：支持把高频多步任务做成组合工具，而不是继续增加工具描述。
- **候选资产**：工具链清单；关键流程确定性编排。

### C11 · 已知答案在转述时走样

- **用户看到的结果**：算法或状态里已经有正确时间，最终短信却把人或时段说错；结构检查只能证明“回复符合工具输出”，不能证明工具输入正确。
- **理想结果**：代码已知的关键事实不应经过自由改写后失真；输入、计算结果、收件人三者都要对齐。
- **初步归层**：事实传递链，不是缺少协调 SOP。
- **已有处理**：统一事实保真层和时间标准化曾覆盖部分路径。
- **仍需验证**：参与者映射、工具输入来源和最终表达能否端到端追踪。
- **候选资产**：结构化消息槽位；Golden Trace 中保留工具输入输出。

### C12 · 针对单个事故不断补规则，复杂度失控

- **用户看到的结果**：同一个排班问题连续多次修补，代码、rubric 和特殊分支持续增长，新场景仍能找到新洞。
- **理想结果**：识别同类失效的共同机制；没有泛化收益的补丁可以不做或撤销。
- **初步归层**：开发方法与系统架构。
- **已有处理**：开始使用统一事实保真层、确定性计算和分层评测。
- **当前决定**：在完成纠正簇、冲突图和基线前，不直接新增生产规则。
- **候选资产**：本账本本身；每个实验的停止条件与回滚条件。

### C13 · 没点名但仍让 B 推断出 A

- **用户看到的风险**：AI 可能删掉投诉者姓名，却把只有 A 才知道的时间、物品或原话告诉 B，B 仍能立即推断来源。
- **理想结果**：隐私验收以合理推断风险为准，不以“有没有出现名字”为准。
- **初步归层**：信息流、收件人知识边界和行动前安全判断。
- **当前默认**：先不发送；用一句话告诉 A 可能被推断，直接问是否仍要发送。A 不接受风险就停止，不为这个情况自动升级给任何人。
- **候选资产**：隐私现场卡、红区触发器、收件人视角验收。

### C14 · 处理效果差却继续装作能协调

- **用户看到的风险**：系统在明显超出当前稳定能力时仍给方案，结果可能比坦白不能处理更糟。
- **理想结果**：基于客观信号识别绿/黄/红区；红区说明具体边界、保留事实并交接。
- **初步归层**：能力管理，不是礼貌性免责声明。
- **当前决定**：能力边界工作线提前，不再等所有提示词实验结束才做。
- **候选资产**：`.claude/CAPABILITY_BOUNDARY_V0.md`。

### C15 · 管理立场漂移，缺乏稳定承托

- **用户看到的风险**：谁最后说话就跟谁走，或给出差异很大的选项让用户替系统承担决定。
- **理想结果**：对人中立，对事实、伤害和权利有稳定标准；新事实改变决定时解释变化依据。
- **初步归层**：决策一致性与权责承担。
- **候选资产**：跨轮 Golden Trace；决定变更记录；中立性验收。

## 横向归因

| 失效层 | 对应纠正 | 当前最值得验证的方向 |
|---|---|---|
| 世界与角色理解 | C01、C03、C08、C13 | 现场卡 + 参与者关系与收件人知识边界 |
| 判断与方案 | C04、C05、C06、C07、C15 | 少量完整成功轨迹 + 结果验收 |
| 行动可靠性 | C09、C10 | 组合工具 + 完成度收据 |
| 事实传递 | C11 | 结构化权威事实源 |
| 表达 | C02 | 多样化示例 + 独立写话验收 |
| 开发方法 | C12 | 一类问题一个机制，不枚举措辞马甲 |
| 能力边界 | C14 | 客观绿黄红信号 + 安全交接 |

## 第一轮优先级判断

优先做 **C13 / C14 / C15** 的边界桌面演练，同时保留 **C04 / C05 / C09** 的成功轨迹实验，用 **C01 / C08** 设计现场卡样例。

原因：老板刚明确隐私、能力诚实和稳定中立是一级红线，应先证明系统知道何时不能行动；其余三项分别覆盖“该不该问”“方案能不能过真实生活”“说了以后有没有真做”的主链。
