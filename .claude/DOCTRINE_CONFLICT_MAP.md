# WillingLink Doctrine 冲突与重叠地图

> 建立日期：2026-09-09
> 性质：只读设计审计，不代表已经决定删改提示词。
> 目标：找出模型在同一情境下可能收到的互相拉扯指令，并区分真正冲突、边界不清和合理分层。

## 判定标准

- **真冲突**：同一上下文中无法同时执行两条要求。
- **边界不清**：两条都可能正确，但提示词没有提供稳定的选择条件。
- **重复负载**：意思接近，散落多处，增加长度却不增加决定信息。
- **合理分层**：生成原则与验收标准相互配合，不应误删。

## 最高优先级的五组拉扯

### 运行时同时装配确认

已核对 `lib/ai/brains/coliving/index.ts`：

- `identity`、`constitution`、`arbitration`、`craft` 四份每轮常驻。
- 一旦消息提到其他住客，或已有未结冲突案，`conflict` 会被强制装入。
- 消息含“投诉、受不了、担心、不安全”等表达时，`complaint-risk` 还会与 `conflict` 同时装入。
- 因此 D01–D03 在常见室友投诉中会真实同时出现，不只是跨文件静态重复。
- `rubric` 不参与生成，只由批判器读取；它与生成原则的重复应按“分层配合”审计，不能当成同轮生成冲突。

### D01 · “不要问怎么处理”与“明确问想达成什么结果”

- `domain/complaint-risk.md:53`：不要问“你希望我怎么处理”，处理方式是协调员职责。
- `domain/conflict.md:17`：不问“你希望怎么解决”，但要问方案“这样行不行”。
- `domain/conflict.md:48-49`：分别私聊时明确问“你希望达成什么结果”。
- `domain/conflict.md:66`：再次允许问“你希望最后变成什么样”。
- **判定**：边界不清，且对弱模型近似真冲突。
- **真正需要的区分**：不能把流程设计推给住户；可以询问住户的利益、底线和期望结果。
- **风险**：模型可能一律不问诉求，也可能换一种措辞把处理责任重新推回用户。
- **候选处理**：用一组正反成功轨迹展示“问结果、不问办法”；后续再决定是否合并文字。

### D02 · “一轮只问第一类个人事项”与投诉事实调查

- `always/arbitration.md:66`：一轮最多问一个问题，且只问第一类；第二类只告知不询问。
- `always/craft.md:8`：一次只问一个问题。
- `always/craft.md:79-80`：只问第一类，能推的不问。
- `domain/conflict.md:48-52`：需要依次问事实、影响、诉求，缺哪项追问哪项。
- `domain/complaint-risk.md:45-55`：受理投诉需要判断影响和处理边界。
- **判定**：真冲突风险。“一次一个”与“只准问第一类”不是同一个限制；后者会封死必要调查。
- **候选处理**：把限制改造成选择条件：一轮一个“会改变处置的缺项”；个人决定必须问，流程决定不问，事实缺口按需问。
- **验证方式**：完整信息与缺一项信息各做一条成功轨迹，观察是否既不拖延也不瞎猜。

### D03 · “协调员直接定”与“共享安排需要参与者确认”

- `always/arbitration.md:42-49`：流程与判断由协调员定，不把决定推回住户。
- `domain/conflict.md:17-19`：方案由协调员算，但共用资源分配要问“这样行不行”。
- `always/arbitration.md:60-66`：规则形成要询问一轮；问过才真正成立。
- `domain/conflict.md:61`：约定写成一条消息即成立，不签字、不要求回执。
- **判定**：边界不清。
- **真正需要的状态区分**：临时默认安排、协调建议、全屋长期规则、当事人已明确约定，不应都叫“成立”。
- **风险**：模型要么过度民主化、每步请示，要么未经参与就把长期规则说成已经成立。
- **候选处理**：现场卡增加 `decision_type` 与 `status`；成功轨迹展示“先给可执行默认，再收一轮反馈”的完整过程。

### D04 · “不要说内部将来流程”与“必须告知必要下一步”

- `always/craft.md:69-73`：避免把“我回头去了解/提醒”等内部流程当回复内容，但必要下一步可以说。
- `always/constitution.md:70-72`：答应联系谁，本轮就联系；只承诺自己能控制的动作。
- `domain/conflict.md:21`：说了要联系谁，本轮必须真的联系到，否则别写。
- `tool/records.md:75-87`：转交必须包含对象、时间、承诺时限和逾期升级。
- **判定**：边界不清，不是完全冲突。
- **真正需要的区分**：空泛过程播报应省略；会影响用户预期、等待和责任归属的下一步必须说，并与真实动作收据一致。
- **风险**：为了避免空头承诺而什么都不告诉用户，或为了显得负责而叙述并未发生的动作。
- **候选处理**：动作状态统一为 `planned / attempted / delivered / replied / agreed / failed`，表达只能引用实际状态。

### D05 · 默认匿名全屋提醒与投诉人对来源暴露的决定权

- `always/craft.md:36-37`：投诉默认采用不点名的全屋口径，不要把匿名方式重新抛给投诉人选择。
- `always/arbitration.md:47`：是否让对方知道投诉来源属于当事人自己决定。
- `domain/complaint-risk.md:64-66`：若只有一人可能提出该投诉，要主动提示可识别风险，再询问是否改变方式。
- `domain/conflict.md:82-86`：保护来源，避免通过措辞反向点名。
- **判定**：边界不清，包含合理例外，但优先级没有被表达成决策树。
- **真正需要的区分**：默认匿名；可识别风险必须告知；明确选择公开来源则尊重；法律或安全例外另行升级。
- **风险**：反复问匿名偏好造成负担，或机械匿名却让全屋一眼猜出投诉人。
- **候选处理**：把它提炼成离线 SOP 决策树，不必保留四处近义散文。
- **运行证据（2026-09-09）**：`corpus-025-cleaning-privacy-2026-09-09` 的一次基线和一次 Golden Trace A/B 都在未询问阿哲的情况下联系大凯；实验组还直接写出阿哲姓名和私人房间细节。运行中的 critic/硬闸曾驳回“告诉阿哲对方可能推断来源并询问是否继续”的草稿，证明这里不是纸面上的轻微重复，而是会把正确动作改写成隐私泄漏的真实冲突。
- **当前决定**：不再用措辞白名单绕过。先建立 `source_owner / proposed_recipient / inference_risk / owner_consent` 决策状态；存在合理反推风险且没有同意时，联系另一方必须处于阻塞状态。

## 高重复主题

### R01 · 一方说法不是事实

分布于 `always/constitution.md`、`domain/conflict.md`、`tool/records.md`、`rubric/rubric.md`。

- **价值**：这是核心原则，不能简单删除。
- **问题**：生成、记录和验收各自重复解释，且“当事人亲口说的能当事实讲”容易被误读成其指控内容已被证实。
- **建议方向**：建立统一术语：`observed_fact / party_claim / system_record / inference / unknown`；各层只引用定义，不重复长篇说明。

### R02 · 承诺必须兑现

分布于 `always/constitution.md`、`domain/conflict.md`、`always/craft.md`、`rubric/rubric.md` 和工具描述。

- **价值**：生成原则与验收相互配合是合理分层。
- **问题**：自然语言版本无法证明动作发生，过去已出现“改个时态绕过验收”。
- **建议方向**：保留一条原则；可靠性主要交给动作状态和完成度机制。

### R03 · 一次只问一个问题

分布于 `always/craft.md`、`always/arbitration.md`、`domain/conflict.md`、`domain/complaint-risk.md`、`domain/tenancy.md`。

- **价值**：短信交互中降低负担。
- **问题**：与“只能问第一类”“不回不追问”“信息缺三项走了解流程”混在一起，模型难以判断何时继续。
- **建议方向**：保留一句交互原则，把“问什么”交给缺项状态而不是固定类别口号。

### R04 · 不依赖监督、选择低摩擦方案

分布于 `always/constitution.md`、`always/arbitration.md`、`domain/conflict.md`。

- **价值**：核心产品判断，适合保留。
- **问题**：目前只有抽象原则，缺少“复杂但公平”与“简单且够用”的对照案例。
- **建议方向**：主要通过 Golden Trace 教会取舍，文字原则只留一句。

## 暂不算冲突的分层

以下内容虽重复，但职责不同，当前不建议贸然合并：

- `always/constitution.md` 的价值原则与 `rubric/rubric.md` 的输出检查。
- `domain/complaint-risk.md` 的风险分级与 `tool/records.md` 的转交留痕。
- `always/identity.md` 的能力边界与具体工具权限。
- 专项 SOP 的领域事实与常驻层的通用原则。

真正的问题不是“同一个意思出现两次”，而是模型是否需要在本轮同时读取所有版本，以及版本之间是否提供了额外决定信息。

## 第一项建议实验

暂不直接删 doctrine。先针对 D01–D03 制作 6 条很短的对照轨迹：

1. 信息齐全：直接给默认方案，不再追问。
2. 缺关键事实：只问一个会改变处置的问题。
3. 询问期望结果，但不让住户设计流程。
4. 临时安排先执行，同时邀请一轮反馈。
5. 长期规则尚未成立，不能冒充全屋已同意。
6. 当事人表达个人边界，由本人决定。

如果少量轨迹已经能稳定解除拉扯，再考虑精简文字；如果仍不稳定，说明需要结构化状态或拆分决策调用，而不是继续改措辞。

六条候选已写入 `.claude/GOLDEN_TRACE_CANDIDATES.md`，目前只作人工审阅和后续基线设计，不接生产。
