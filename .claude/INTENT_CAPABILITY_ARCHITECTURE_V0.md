# 用户意图 × 能力模块架构 V0

> 日期：2026-09-10
> 性质：离线开发草案；不接生产，不证明模型已经会正确拆意图或稳定完成协调。

## 为什么要加这一层

当前系统已经有 doctrine、上下文、工具和 V4 逐动作计划，但缺少一个明确回答：住户这次究竟想让
系统达成什么结果，系统准备用哪一种能力承接，以及这项能力的边界在哪里。V0 把这一层单独表达：

`住户原话 → IntentEnvelope → 能力选择 → V4 逐动作计划 → 工具与收据 → 对外回复`

这条链是工程设计，不是 doctrine 原文。Doctrine 提供决定权、隐私、事实来源、公平、承诺兑现
等业务不变量；代码结构负责让这些不变量可检查。

## 三类东西必须分开

1. **Capability**：一个动词加一个可验收结果，可以被动作计划调用。
2. **Cross-cutting policy**：隐私、事实来源、决定权、公平、完成收据；约束多个能力，但本身不是动作。
3. **Domain playbook**：访客、噪音、清洁、金钱、排班；只在相应话题检索，不复制成同构能力。

## 首批七个能力模块

| id | 可验收结果 | 成熟度草案 | 主要边界 |
|---|---|---|---|
| `send-targeted-message` | 指定第三方收到一条最小化消息，并产生其投递收据 | available | 只允许 `contactPerson`；不把回复当前发信人的 `sendReply` 混进来 |
| `collect-constraint` | 一名参与者的时间或边界被问到并记录 | partial | 联系与记录是多步链，可能只完成一半 |
| `draft-schedule` | 穷举候选并选定唯一内部草案 | partial | `pickSchedule → chooseSchedule` 曾有漏调用、心算和链路耗尽事故 |
| `distribute-schedule` | 每位受影响者收到自己的时段，份额与影响关系有记录 | partial | 多人投递、记录和等待状态容易漏 |
| `circulate-rule` | 共同规则提议发给相关居住者，逐人立场入库，问全后才成立 | partial | 已发送不等于已同意；参与范围不能默认等于整屋名册 |
| `open-conflict-followup` | 主张按来源记录、另一方被联系、案件进入明确等待状态 | partial | 单方陈述不能定性；来源可反推时先停 |
| `decide-cost-split-without-basis` | 无既有依据时由 AI 创设费用承担规则 | blocked | 当前不允许工具和成功收据，不得揽下 |

这里的 `available` 只表示已有确定性执行构件和可核验回执，不等于模型路由、编排或线上效果稳定；
`partial` 表示构件存在但组合链有事故证据；`blocked` 表示当前版本不能独立执行。

## IntentEnvelope

一条消息可以拆成多个意图。每个意图只有六个业务字段：

- `desiredOutcome`：用户想达到的结果；
- `capabilityId`：当前请求动作选择的能力；
- `target`：作用对象；
- `authorizationEvidence`：授权原话，未授权为 `null`；
- `constraints`：只约束本意图的原话限制；
- `completionCriteria`：怎样才算完成。

`id` 只用于结构引用，不算业务字段。V4 的 status、依赖和收据不复制到意图层。

## 当前确定性门禁

- 授权与限制证据必须是本轮原话子串；
- capability id 和 allowed tool 必须在当前 registry / 生产工具声明中存在；
- blocked 能力没有允许工具和成功收据，也不能标为 executable；
- 未授权，或带 `preview_before_publish` / `hold_before_send`，不能标为 executable；
- `conceal_source` 只限制披露方式，不自动等于禁止发送；
- 一项限制只作用于它所属的意图，不能把整条消息连坐；
- 工具名存在只证明构件存在，不证明能力可靠。

## 三张离线样例

1. 简单提醒：单意图、单第三方联系能力；证明普通小事不用复杂卡。
2. 先问小王、再排草案、发信人点头后发布：三个意图分别拥有授权和限制。
3. corpus-024：访客规则是 partial；无依据的新费用分摊 blocked；需要请求人确认是否接受只做较窄范围。

这些映射均为开发者草案，非模型生成、非老板核准。报告与 119 项离线检查只证明结构一致，不能
证明模型能从新原话正确拆解，也不能证明生产端到端效果。

## 下一步候选

先由老板人工查看三张报告。若结构有用，再用少量留出语料做“模型只填 IntentEnvelope”的离线基线，
观察拆分、授权、限制和能力选择错误；在此之前不接 `runColivingTurn`。若模型填卡仍频繁犯常识错，
优先缩小能力选择空间或加入检索样例，不继续增加字段。
