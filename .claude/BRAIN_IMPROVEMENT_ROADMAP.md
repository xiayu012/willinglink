# WillingLink 协调大脑动态改造路线图

> 建立日期：2026-09-09
> 性质：长期连续性文件；不是一次性实施方案，也不是已经批准的技术规格。
> 维护方式：每轮实验后更新“当前判断、证据、下一步”，允许删改路线，不为维护旧计划而维护旧计划。

## 新会话如何接上

1. 先读 `.claude/PROJECT_STATE.md`。
2. 再读本文件的“当前结论”“下一步队列”“决策记录”。
3. 需要了解具体事故时，再查 `.claude/AGENT_LOG.md`；不要重新从头猜问题。
4. 涉及产品行为的实现仍遵守 `AGENTS.md`：Claude Code 实现，Codex 调查、派单、审查、验收、提交。

## 当前结论

WillingLink 不再以“让一个 LLM 独自成为罕见的顶级人类协调员”为默认前提。

更现实的产品目标是：

> 建立一个有记忆、有程序、会沟通、知道何时不能独自判断、能把复杂问题交接出去的协调系统。

当前问题不是单一的“提示词不够详细”：

- **大脑**：原则很多，成功示范少；部分规则重复甚至冲突。
- **眼睛**：名册、规则、案件、等待对象、历史表态都能看到，但信息分散，缺少聚焦的本轮现场卡。
- **手脚**：工具齐全但颗粒太碎；复杂场景依赖模型自己记住长工具链。
- **能力边界**：系统仍倾向要求模型对所有情况给出答案，没有足够可靠的“停止判断并升级”机制。
- **模型上限**：生产默认便宜模型适合大量日常工作，但长上下文、多方判断、多工具编排的组合难度可能超过其稳定能力。

2026-09-10 新增证据：写话的“简洁”曾被错误执行成没有理由的冷硬命令；动作的“主动推进”曾被错误执行成连没有可靠处理能力的费用分摊也先揽下。下一轮先修离线期望与能力表示，不把这两个问题继续归咎于提示词字数或模型价格。

因此改造方向不是“把人类思维全写成代码”，而是重新分工：

| 层 | 负责什么 | 不负责什么 |
|---|---|---|
| 确定性代码 | 状态、计算、权限、隐私、动作完整性、失败检测 | 人际价值判断、具体措辞 |
| LLM | 理解自然语言、提取事实与诉求、类比案例、生成自然表达 | 保证长工具链不漏步骤、裁决不可核实事实 |
| 成功案例与 SOP | 提供成熟做法、示范判断路径、帮助模型类比 | 作为必须逐字执行的无限规则库 |
| 人类或更强模型 | 高风险、事实冲突、罕见复杂局面、价值权衡 | 日常重复提醒和机械记录 |

## 目前需要验证的假设

下面都是可被实验推翻的假设，不是既定答案。

### H1 · 成功轨迹比继续增加禁令更能改善行为

当前 doctrine 主要告诉模型“原则是什么、什么不能做”，很少展示一段完整的优秀协调过程。
候选方向：为每类高频任务提供少量、相关、多样的成功轨迹。

成功轨迹不只是最终一句回复，应包含：

1. 当时的房屋状态；
2. 当前入站消息；
3. 已知事实与未知项；
4. 判断和权限边界；
5. 实际工具动作及结果；
6. 发给其他住户的消息；
7. 给当前住户的最终回复；
8. 为什么这样处理。

运行时只检索最相关的 2–4 条，不把案例库整包塞入上下文。

### H2 · 提示词冲突和重复正在制造随机行为

已发现的明确例子：

- `domain/conflict.md` 前面写“不问你希望怎么解决”，后面又要求明确问“你希望达成什么结果”。
- `always/arbitration.md` 说一轮只问“第一类”个人事项，但投诉 SOP 又要求询问影响、诉求、处理接受度。
- 决定权、提问规则、方案是否征询在 constitution、arbitration、conflict、craft 多处重复表达。

候选方向：每个决策只保留一个权威来源；其它文件引用它，不重新解释。

### H3 · 本轮现场信息需要从散文变成结构化任务卡

候选“本轮现场卡”字段：

```text
说话人
当前事项
本轮意图
已确认事实
各方陈述（标明来源）
未知且会改变结果的事项
正在等待谁回复
已经做过的动作
本轮必须完成的动作
本轮不得做的动作
可用权限与工具
需要升级的触发信号
```

目的不是给模型更多信息，而是减少它自己从长历史里拼装当前任务的负担。

### H4 · 最大技术收益可能来自组合工具，而不是提示词

典型失败链：模型需要自己完成
`decide → recordPosition → pickSchedule → chooseSchedule → contactPerson → sendReply`，
任何一步漏掉都会产生看似会说、实际没做的结果。

候选方向：把容易漏的确定性流程组合成更高层动作，例如：

- 共享设施协调：记录约束、计算、选定、通知受影响者、返回已发生事实；
- 冲突受理：建案、记录单方陈述、联系另一方、登记等待状态；
- 共同规则形成：提出默认、逐个征询、记录异议、收口；
- 转交闭环：记录、送达、设定跟进、超时提示。

LLM 仍决定语义输入和最终说法；代码只保证动作顺序、事务完整性和事实真实性。

### H5 · 判断、行动、写话不应全部挤在一个模型调用里

候选结构：

```text
判断器：输出结构化判断与下一动作
    ↓
行动层：调用确定性工具，得到真实执行结果
    ↓
写话器：只看已发生事实 + 少量成功示例，写一条自然短信
```

这样写话器不需要同时管理十几个工具；行动失败也不会被文案润色掩盖。

### H6 · “处理不了”不能依赖模型自我感觉

不问模型“你有多大把握”。系统根据外部可观察条件决定绿/黄/红区：

| 区域 | 条件 | 行为 |
|---|---|---|
| 绿色 | 事实够、风险低、可撤销、有工具、有相近成功案例 | AI 可独立完成 |
| 黄色 | 缺一个关键事实、有人未表态、存在多个合理解 | 只问关键缺项或给明确暂定方案 |
| 红色 | 事实冲突、无权限、无可行方案、高风险、工具失败、反复无进展 | 停止裁决，记录并升级 |

需要程序化识别的信号包括：

- 必要事实缺失；
- 双方说法冲突且无可核实证据；
- 只有单方陈述却准备给另一方定性；
- 需要身体、现场观察、法律权限或支付权限；
- 排班器返回无可行候选；
- 涉及安全、歧视、报复、非法驱逐、严重金钱或住房风险；
- 工具调用失败或消息未送达；
- 连续两轮没有实质推进；
- 用户再次纠正同一类问题；
- 找不到相近成功案例，或两个独立判断明显分歧。

### H7 · 模型应该按难度分流，而不是全屋统一使用一种强度

候选分流：

- 简单查询、记录、提醒：便宜模型；
- 普通冲突、多人安排：经过验证的较强模型或结构化组合流程；
- 高风险、罕见价值冲突：人类审核，必要时更强模型只做辅助分析；
- 最终是否切换模型必须用同一批现实回放做 A/B，不凭主观印象。

## 现有提示词大脑中的 SOP 资产

这些资料很有价值，但用途要从“全部在线约束模型”扩展为：我们设计流程、成功案例、升级规则和验收标准时的业务教材。

### 1. 身份与能力边界

来源：`lib/ai/brains/coliving/doctrine/always/identity.md`

- AI 协调员，不是管理员；
- 语言、信息、记录、调度四种能力；
- 没有身体，不在现场；
- 住户、房东与协调员的角色边界；
- 服务对象的注意力、设备和住房退出成本。

可转化为：能力边界卡、工具权限表、不能独立处理的条件。

### 2. 通用判断原则与优先级

来源：`always/constitution.md`、`always/arbitration.md`

- 问题分类：共用分配、后果责任、安全、合同；
- 事实、系统记录、推测分离；
- 公平、可执行、参与、隐私、尊严；
- 分配前的计算闸、记忆负担闸、监督负担闸、结果合理性闸、推进闸；
- 决定权归属；
- 安全与住房稳定优先级；
- 禁区。

可转化为：规划器判断字段、确定性验证器、升级规则。需要先去重和解决冲突。

### 3. 投诉受理与风险分级

来源：`domain/complaint-risk.md`

- 主动询问节奏；
- 受理硬规则；
- 事实、影响、此前沟通、诉求、可接受处理方式；
- 投诉来源暴露程度；
- P0–P3 风险分级；
- 暴力升级、家庭暴力、心理健康、盗窃、经济困境、房东风险；
- 必须上报条件；
- 纠错和反馈闭环；
- 跨案件趋势分析。

可转化为：风险路由器、升级工具、人工审核队列、成功受理案例。

### 4. 异步冲突调解

来源：`domain/conflict.md`

- 判断信息是否已经足够；
- 行为/身份、摩擦/越界、人的问题/房屋问题三组辨别；
- 分别私聊、事实化、向另一方求证、形成约定、复查；
- 恢复性提问；
- 保护投诉人；
- 调解失败后的转向。

可转化为：异步案件状态机、另一方联系流程、冲突类成功轨迹。需要先解决内部提问规则矛盾。

### 5. 入住、规则执行与离开

来源：`domain/tenancy.md`

- 入住信息分批收集；
- 首次接触与开张流程；
- 违规事实与后果分离；
- 0–5 级处置阶梯；
- 一致执行；
- 新住户加入、租期变更、主动退租；
- 非自愿离开的绝对边界。

可转化为：入住状态机、处置权限表、强制人工节点。

### 6. 记录、转交与拒绝不当指令

来源：`tool/records.md`

- 可核实事实、某方陈述、系统评估、未知项分栏；
- 精简记录字段与送达记录；
- 转交四要素与闭环；
- 谁负责什么；
- 拒绝不当指令的三级链条。

可转化为：统一案件数据结构、转交事务工具、拒绝/升级成功案例。

### 7. 高频专项 SOP

来源：`special-cases/*.md`

- 排班：共用范围、独占安排、容量、反对后的重算、卫生间倒排；
- 金钱：租金、押金、公用费用、私人债务、剥削信号；
- 规则：推送时机、安静时段、规则正当性；
- 清洁、噪音、储物、访客的最小处理原则。

可转化为：按话题检索的短 playbook、组合工具输入规则、对应成功轨迹。

### 8. 输出验收清单

来源：`rubric/rubric.md`

- 收信人角色是否正确；
- 是否编造；
- 是否回应当前消息；
- 责任是否落对人；
- 分配是否算过且合理；
- 是否依赖记忆与监督；
- 承诺动作是否真的完成；
- 是否泄露隐私、只听一边、暗示失去住处；
- 是否冷硬、使用占位名或客服腔。

可转化为：离线评测维度、确定性检查、老板纠正分类标签。不是所有项目都应在生产中调用 LLM 批判器。

## 动态工作线

这些工作线可以并行、暂停、合并或调整顺序。

### 工作线 A · 失败与老板纠正账本

目标：把过去“又得老板纠正”的经历变成可查询数据，而不是聊天记忆。

最小字段：

```text
事故 id
真实/合成来源
当时状态
住户原话
AI 原动作与原回复
老板指出的问题
最终认可方向
失败发生在哪一层：看错 / 判错 / 动作漏了 / 说错 / 系统故障
对应 SOP
是否适合作为成功示例
是否已有回归场景
```

### 工作线 B · Golden Traces 成功轨迹库

目标：建立老板认可的少量高质量示范，而不是追求数量。

准入条件：

- 真实或人工刁钻场景；
- 所有事实来源清楚；
- 工具动作与消息内容一致；
- 老板认可，或通过明确人工验收；
- 与测试留出集隔离，避免拿答案测答案。

需要覆盖的首批类型：

1. 简短接住住户，不说内部流程；
2. 只听一方时如何联系另一方；
3. 排班约束收齐、计算、通知到人、自然回复；
4. 对方反对后真正调整，不重复旧方案；
5. 信息不足时只问一个关键问题；
6. 事实冲突时不裁决；
7. 工具失败时如实告知未完成；
8. 超出能力或权限时完成交接；
9. 金钱困难与住房风险；
10. 安全敏感但不越权的处理。

### 工作线 C · Doctrine 精简与 SOP 提炼

目标：把同一份知识拆成四种产物：

1. 少量真正常驻的不变量；
2. 按情境加载的短 playbook；
3. 供代码执行的确定性约束；
4. 供我们与人工审核使用的完整 SOP 手册。

方法：先画重复/冲突图，再删改；不从“重写一份更漂亮的提示词”开始。

### 工作线 D · 本轮现场卡

目标：让模型无需自己在长历史中拼装当前任务。

先做离线样例，确认字段真的帮助判断，再考虑接入生产。若卡片比现有 prose 更长或重复信息更多，停止并重新设计。

### 工作线 E · 手脚重组

目标：找出模型最常漏步骤的工具链，逐步合并为高层事务动作。

优先候选：

1. 多人排班完整链；
2. 冲突受理与联系另一方；
3. 共同规则逐个征询；
4. 转交与跟进闭环。

边界：代码保证动作完整，不替大脑硬编码住户话术和价值判断。

### 工作线 F · 能力边界与升级

目标：不依赖模型自报信心，通过可观察信号决定继续、询问或升级。

需要明确：

- 升给谁；
- 升级时需要携带哪些事实；
- 对住户怎样解释；
- 上报后谁负责继续跟进；
- 没有人可接手时怎样保持诚实、不制造虚假承诺。

### 工作线 G · 模型与调用架构实验

候选实验：

- 当前单模型基线；
- 当前模型 + 动态成功示例；
- 当前模型 + 结构化现场卡；
- 判断/行动/写话拆分；
- 复杂场景选择性使用更强模型；
- 两个独立判断在高风险场景做分歧检测。

只用同一批固定回放比较，不因某一次输出惊艳就切换。

## 柔性阶段安排

### 阶段 0 · 建立共同认知与基线

先做：

- 汇总已知真实失败与老板纠正；
- 建立 doctrine 重复/冲突地图；
- 给现有场景按“看、判、做、说、升级”分类；
- 记录当前模型、延迟、成本和失败分布。

退出条件：我们能回答“它主要在哪一层失败”，而不是笼统说“大脑不聪明”。

### 阶段 1 · 小规模成功示例实验

先不重构全系统：挑 3 类高频问题，各准备 3–5 条成功轨迹；候选版本动态检索少量示例。

退出条件：在留出场景中稳定减少同类错误，且没有明显模仿固定话术、泄漏案例事实或增加冗长。

若无改善：检查示例质量、检索和模型能力，不继续堆案例。

### 阶段 2 · 提示词去重 + 本轮现场卡

根据阶段 0 的冲突图删除重复规则；以对照实验判断现场卡是否降低遗漏和答非所问。

退出条件：提示更短、冲突更少，正确率不下降；不是以“字数变少”冒充成功。

### 阶段 3 · 重组最脆弱的手脚

只处理证据最多的一条工具链，优先多人排班或冲突受理；验证后再决定是否扩展。

退出条件：工具漏调用、虚假承诺和半完成状态显著下降。

### 阶段 4 · 能力边界和分级路由

建立绿/黄/红条件，先影子记录“如果上线会不会升级”，确认不过度升级后再真实启用。

退出条件：复杂情况能被及时识别，普通小事不会大量推给人工。

### 阶段 5 · 决定是否拆模型、换模型或做自动提示优化

只有前面数据表明问题确实来自模型能力上限，才投入更强模型、分阶段调用或 DSPy/MIPRO 等自动优化。

## 验收指标

不追求一个虚假的“智能分数”。同时看：

### 用户结果

- 老板每 100 个测试轮次需要纠正多少次；
- 同一类问题是否重复纠正；
- 住户是否得到明确、与自己相关的下一步；
- 消息是否短、自然、不像客服或内部流程播报。

### 行动可靠性

- 承诺动作完成率；
- 受影响者通知完整率；
- 重复联系率；
- 状态记录正确率；
- 工具失败后虚称成功率；
- 连续无进展轮次。

### 判断边界

- 单方陈述被误写成事实的次数；
- 高风险漏升级率；
- 普通事项过度升级率；
- 无权限事项越权处理率；
- 事实冲突时擅自裁决率。

### 工程成本

- 单轮模型调用次数；
- 输入 token、输出 token；
- 延迟；
- 模型费用；
- 新规则或示例带来的回归数量。

## 实验纪律

- 先用离线确定性闸；模型评测按场景定向运行。
- 不对真人住户做试验，不走真实 Twilio，不伪造真人历史。
- 候选版本先影子跑或隔离测试屋。
- 成功案例池和最终留出测试集分开。
- 同一轮实验只改变一个主要变量；否则无法判断收益来自哪里。
- 模型输出有随机性：关键结论至少观察多个不同场景，必要时少量重复，不用一次结果定方向。
- 每个实验都允许得出“这个办法没用，停止”的结论。

## 动态转向规则

| 观察到的证据 | 优先调整方向 |
|---|---|
| 同类措辞反复被老板纠正，但动作正确 | 成功示例 / 写话器 |
| 事实和对象经常看错 | 本轮现场卡 / 历史组织 |
| 知道该做却漏工具 | 组合工具 / 行动层 |
| 提示词不同条款互相拉扯 | doctrine 去重与权威来源 |
| 普通场景稳定，高难场景随机 | 难度路由 / 更强模型 / 人工升级 |
| 加示例后只会模仿固定句式 | 提高示例多样性、减少示例、改检索 |
| 提示更短但行为变差 | 恢复必要原则，不把压缩当目标 |
| 人工升级太多 | 缩窄红区、增加黄色暂定处理 |
| 高风险仍漏掉 | 扩展确定性风险信号，不靠模型信心 |
