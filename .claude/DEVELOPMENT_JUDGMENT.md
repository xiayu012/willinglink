# 开发判断约定：先审需求，再审实现

状态：2026-09-10 老板要求建立的开发协作约定。适用于 Codex 与 Claude Code；不是生产 doctrine，不加载到住户对话。本文是开发方法，不宣称已有实验证明它能消除模型错误。

## 本次事故与责任

Codex 把“AI 应承担协调工作”扩大成“每轮必须出站”，被老板指出可以先讨论后，又收窄成整轮 deliberating/authorized 二选一。缺少的是需求判断：一个目标可能包含多个动作，每个动作的授权、信息与完成条件不同。Claude 按任务实现，Codex 按自己的任务验收，形成共同前提错误。更换模型不能替代这一层验收。

92 项确定性检查通过，只证明这些断言通过；三张手写期望卡通过，只证明样例与校验器相容。两者都不证明在线模型会协调，也不证明老板认可样例。不得用“金标准”“人工核准”包装开发者自己的草案。

## 后续模型的默认做法

接到纠正，先恢复目标、已有事实和原话的适用范围。不要把一句纠正直接翻成全局 must/never、枚举或正则。先问自己：这条规则会不会拒绝一个正常的好行为，或者放行一个明显的坏行为？自己给出能推翻提案的日常反例，不把找例外的工作交给老板。

区分这三个层次：产品目标（AI 承担协调成本）；本次授权（允许哪一个动作、面向谁、在什么条件下）；执行证据（工具实际上做成什么）。它们不能互相替代。表达简洁不意味着省去必要信息；承担协调不意味着擅自决定共同权利；获准执行不意味着本轮已有足够信息、已有结果或必须发消息。

业务依据先读相关 doctrine 原文，写明条款与适用条件。来源文件名、权威机构名称或来源标签不能证明某条具体规则成立。老板明确产品要求优先，但须保留其上下文；发现 doctrine 冲突则标明冲突，不能任选一句当依据。工程推导明确标为推导，不伪称来自资料。原有 doctrine 的“共同的事，让受影响者有机会说话”“流程由协调员负责”“只承诺能控制的”应同时考虑。

## 开工前的短规格（写入当次任务，不另建层层清单）

- 原始需求与来源：引用必要原话，定位相关 doctrine；用一句话说明要改善的住户结果。
- 当前证据：是哪条输入、上下文、实际输出出了问题；缺证据则标为待验证推断。
- 适用边界：正常应做、正常不应做、只改变一个条件就应改变选择的三个例子。例子不固定三个类别，也不要求每次增加机器测试。
- 最小改动与验收：改哪一层、依据什么判断成功；说明哪些结果仍未验证。优先修错误前提或删除矛盾，避免扩充状态机来掩盖问题。

## 双模型的独立性

Codex 给 Claude 原始需求、必要上下文、产品约束和可反驳的提案。Claude 开始实现前先检查提案是否与原始需求冲突；若找到反例，先回报，不能为了照单完成而编码错误规则。

Codex 验收先读原始输入及用户可见结果，再读实现与测试。至少检查一个不由实现断言直接定义成功的相邻情境。测试失败不能通过改写输入来消除；语料转化保留请求强度、保密限制、人物关系和先后条件。确需改原始输入，保留原版并标明新版本的用途。

老板不负责逐个发现普通语义、授权、状态和话术错误。只有资料无法决定且不同选项会实质改变产品方向时才问老板；常识、读取资料、反例检查由开发者完成。

## 用这次问题检验判断（审查示例，不是固定回复或生产 SOP）

| 情境 | 应有判断 | 会暴露什么错误 |
|---|---|---|
| “先帮我拟个过夜规则，别发，讨论好再通知” | 给可讨论的具体草案，保留未确认条件 | 把管理目标等同立即出站 |
| “就按刚才确认的提醒小王” | 结合历史执行那次已授权提醒 | 重复索取已经给出的许可 |
| “先问小王哪天方便，排好表先给我看” | 可联系收集信息，尚不可发布排班 | 整轮只能讨论或只能执行的二分法 |
| “帮我安排时间”，但本人的关键可用时间未知 | 先补会改变安排的缺项；不捏造也不强行联系别人 | 已授权被等同信息充分 |
| “算两种排班给我比较，暂不通知” | 计算/准备也是工作，无第三方消息很正常 | 管理动作被等同短信 |
| “请提醒他进门敲门”与“但别让他知道是我说的” | 前者执行最小必要提醒；后者若与推断风险冲突则解决该冲突 | 忽视已授权，或忽视附带限制 |
| 发送工具失败；或先前已发、正在等回复 | 如实报状态并按已有机制处理，不假称成功或为过闸重复发 | 用出站数组代替执行证据 |
| AI 负责形成共同规则 | 主动准备与协调，依据参与和决定权形成规则 | 把“不推责任”扩大为“独断” |

这些例子说明需要保留动作范围与阶段，不是要求立刻把每种情况写成新字段。先核对现有模型能表达什么，再决定必要的工程改动。

## 证据与节省成本

报告分清：开发者期望样例、离线结构检查、真实模型输出、工具执行结果、老板明确认可。模拟里的“已发送”是期望台词，不能当真实发送回执。只展示人工编辑样例时，不声称模型表现已改善。

日常实现继续按既有 Claude Code 分工和免费检查纪律。把更强模型的预算集中用于新业务抽象、权限变化、评价标准和反复失败的设计审查；稳定规格的实现与常规验证可继续用成本较低的配置。这是工作安排建议，不是模型能力比较结论；不自动切换模型或增加付费调用。相同类别连续被纠正时，暂停该设计的扩展并复查前提，不能继续加补丁后宣称治本。

## 当前遗留：V2 不具备生产接入验收

已查到 `lib/chat/coliving/evals/privacy-turn-card.ts` 的 `authorized_requires_outbound` 仍将已授权的整轮等同于必须出站；`deliberating` 整轮禁止出站，不能自然表达“先联系调查，方案另行确认”。这些是本轮发现的反例覆盖缺口，不是已修复项目。

024 的“我来定具体规则”仍须按共同事项的参与权检查，不能因短就认定好。当前三张报告是开发者编写的离线期望草案，尚未获得老板对此版本的明确认可。本轮只建立开发约定；后续产品改动须交 Claude 实现、独立验收，不以本文替代产品验证。
