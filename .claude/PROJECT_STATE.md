## 产品一句话

WillingLink 是合租/多人 AI 协调系统：LLM 理解查询，合租「大脑」通过短信协调
多人排班、规则、冲突与入住。核心资产是分层提示词（doctrine）、critic 与确定性
闸，不是通信管道。

## 当前工作线（倒序）

### 最新（2026-09-13 默认宽容）：已批准清单是优化快路径，不是权限边界

- **功能**是老板批准的**唯一正式最小产品单位**（各写各的朴素代码，不强行抽象）；`intent`
  只描述本轮目的与阶段；**工具只是底层机械动作**。当前写死的已批准清单只有两项：
  **个人物品使用提醒**、**夜间洗衣机/烘干机提醒**（`lib/chat/coliving/features.ts` 的
  `APPROVED_FEATURES`）。
- **清单不再是权限边界，而是一条低成本、稳定的优化快路径**：命中时 `turn.ts` 在
  `buildContext` 之后、主生成之前走**功能前门**，做**一次**内部路由（只能在清单 id、`none`、
  `reply_only`、黑名单 `blocked:<id>` 里选一个；不是 LLM tool、不新增 tool schema），命中
  就由**被选中那一个功能**抽取本功能获准的有限结构字段、生成正文，再由纯代码
  `sms-delivery.ts` 绑定原话点名且唯一的收件人并落库；命中轮 `toolsUsed` 为空、
  `promptComposition` 为 `null`。
- **只有整条交办恰好完整落在一个优化功能里才走快路径**：同一句话里只要还夹带另一项**需要
  执行**的诉求（另一个优化功能，或任何清单外请求），路由就返回 `none`，**整条交给完整主
  流程**——不截走一段、不静默丢掉其余。否定 / 征询 / 附条件的**单一功能**请求走
  `reply_only`（无工具、无出站，只回当前说话人）；「同时交办两件」**不属于** `reply_only`，
  走 `none`。
- **清单外请求不再因「不在清单里」被自动拒绝**：前门返回 `none` 就落回**完整的 doctrine +
  运行时主生成**，那里恢复了**通用短信联系能力 `contactPerson`**（常驻主生成工具表）——
  **是否该替住户去联系某位同屋人，由 doctrine 情境准则 + 本轮 intent 判断**（不是代码按
  关键词，也不是新加「住户必须明说才准联系」的窄规则）。**假完成保护不变**：无实际接受出站
  不得声称已联系；有实际接受出站不得误替换。
- **恢复通用联系 ≠ 恢复来源泄露；默认匿名由代码闸保证**：`contactPerson` 在真正入队前过
  一条纯代码来源隐私闸 `checkSourcePrivacy`（`turn.ts`）——正文**不得出现发信人姓名**、
  **不得把请求归因给来源人**（「他想请你…」「她说让你…」「有人反映…」）、也**不得转述来源
  人的私人处境**（高精度枚举的睡眠状态：失眠 / 没合眼 / 没睡好 / 没睡着 / 补觉 / 睡不着 等），
  命中就拒绝这次发送、让同一轮模型改成中立说法，**不进 contacted/outbound、不落库**；目标
  收件人姓名允许出现，`声音大 / 影响别人休息 / 夜里容易影响休息` 这类共享可观察的必要理由
  必须放行。**当前没有「来源人明确同意暴露」的例外**（一律匿名更安全）。起因是 029 模型验收
  抓到的真实出站泄露：先出现「小婷」+「补觉/睡不着」+「她想请你」，清掉姓名与归因句后仍写成
  「房间里有人补觉、睡不着」，generation-only 下无 critic，靠这条确定性闸兜底；该闸只收能
  高精度枚举的睡眠状态，**不假装覆盖所有语义隐私**。离线检查与 corpus-029 的
  `outboundMustNotMatch` 同步加严，工具 description 也改成"只发共享可观察事项 + 请求动作"。
- **真正办不了的只有一个来源：显式黑名单**（`lib/chat/coliving/blacklist.ts` 的
  `BLACKLISTED_CAPABILITIES`，**当前登记唯一一项「卫生整改要求」`hygiene-rectification`**：
  住户点名室友、要 AI 去**要求对方动手清理**地漏 / 头发 / 浴室等卫生残留、整改卫生；登记
  原因如实保留——系统看不到现场严重程度、当前技术还不能可靠判断「脏到什么程度才适合替一方
  要求另一方整改」，不是因为问题不重要、也不是让住户自己处理）。它**复用前门那一次路由**，
  条目以 `blocked:<id>` token 摆给模型，**只有模型判定住户正在交办该项时**才拦；**不按
  关键词、不加第二次 LLM 调用**。**表里没有的事项、或经讨论 / 否定 / 引用 / 提问（只说
  异味 / 想开窗 / 讨论清洁安排 / 普通抱怨）都不拦**。只服务旧 default-deny 的
  `unsupported.ts` 已删除。当前黑名单适用面与两项快路径相同——「对点名的同住人执行某个功能」
  这一类，不假装覆盖更多形态。
- **产品功能问答**（`feature-qa.ts` + `feature-facts.ts`）口径同步：两项只是**专门优化、
  更快更省**，不是全部能力；其它协调请求走完整协调流程、**不是不能做**；只有黑名单里登记、
  且**与当前问题对得上**的事项才说「办不了」并保留登记原因，没选中条目时**不得虚构
  「不能做」**。不读旧 doctrine、零工具、零第三方出站。
- **企业微信、小红书私信、cron 主动发起（outreach）、LLM 批判器 / 重写仍全部收回、不恢复**；
  生产仍是 **generation-only**。
- **长期会再切回「清单外一律拒绝」**，届时只改 `blacklist.ts` 数据 / 路由，**现在不写双模式
  死代码**（见 `docs/FEATURE_RUNTIME_ARCHITECTURE.md`）。
- 免费闸 `pnpm coliving:quality` + `tsc --noEmit` + `git diff --check` 通过；tsc 仅剩仓库既有
  `speech-input.tsx` 两条 TS2717。未向真人发送短信、未跑模型评测、未 commit/push。

### 历史（已被 2026-09-13 默认宽容取代）：白名单即权限边界（严格口径）

> 本节是 2026-09-13 早先严格口径的历史记录：当时把已批准清单当权限边界、清单外一律用
> `unsupported` 保留轮拒绝。**已被上面的默认宽容取代**——清单外不再自动拒绝、落回完整主
> 流程，`unsupported.ts` 已删除。下面的验收记录与「白名单外仍不做」表述都是当时口径，不得
> 当作现行行为。

- 用户能力说明与内部技术说明已经分开：`docs/USER_FACING_CAPABILITY_TRUTH.md` 只保存功能、
  开发/暂缓理由和拒绝解释；原技术长文移到 `docs/FEATURE_RUNTIME_ARCHITECTURE.md`。以后老板
  批准、暂缓或改变功能边界时，同轮自动更新前者；未给出的理由不编造。
- **功能**是唯一正式的最小批准单位、产品实现单位和白名单执行单位；`intent` 只描述用户当前目的与阶段；**工具**只是底层机械动作，不决定权限。当前不再设置“任务能力”集合层。允许各功能拥有独立、朴素、暂不共用的代码，不为了抽象优雅把边界重新揉成通用动作卡。
- 当前白名单只有两项功能：**个人物品使用提醒**、**夜间洗衣机/烘干机提醒**。`features.ts` 先做一次内部纯文本白名单路由；命中后只有被选中的功能抽取自己的有限字段并生成自然短信。生成阶段看不到原始混合请求和来源细节；`sms-delivery.ts` 只负责绑定原话中唯一点名的收件人并投递，不是模型工具。
- `reply_only` 与 `unsupported` 都是路由保留结果，不是功能：前者承接已批准功能的讨论、否定和条件轮；后者承接明确要求联系室友、但主题不在白名单的请求。两者都无工具、无第三方出站，只对当前用户自然说真话，避免落回旧主流程误调用 `proposeRule` 或谎称已经联系。
- 真实发送功能轮复用 `deliverSms` 已建立的 `contact_one` decision；回执不再重复建立 `reply_only` decision。路由、抽取、生成和保留回复的真实 usage 全部并入本轮账本。
- 白名单外仍不做：卫生/头发、费用、规则、一般噪音、电视音量、通用代转达等不能借相近入口混入。用户明确追问边界时按 `docs/USER_FACING_CAPABILITY_TRUTH.md` 如实解释；普通回复不主动背能力清单。
- Codex 独立模型验收：corpus-034 结构通过且逐轮人工通过，混合请求只发送洗衣提醒，否定/条件轮零工具零出站，费用 `$0.022918`，报告 `tests/coliving-eval/reports/2026-09-13T04-30-01-980Z.html`；corpus-029 结构通过且人工通过，电视音量请求走 `unsupported`、零出站，费用 `$0.000599`，报告 `tests/coliving-eval/reports/2026-09-13T04-45-22-954Z.html`。两次均用 `--judge-off`，自动语义 judge 未运行，不得把“未验收”状态误读成结构失败。
- corpus-035 两轮实测已通过 Codex 人工验收：卫生整改交办只如实说明未发送，不替用户编其它处理方案；紧接追问时会说明「看不到现场程度、不能可靠判断是否达到要求别人整改的地步」，并完整列出两项开放功能。最终一次费用 `$0.001245`，报告 `tests/coliving-eval/reports/corpus-035-generic-feature-qa-final-2026-09-13.html`；`promptComposition=null`、零工具、零第三方出站。
- 本轮还修复了一个真实数据库根因：`decision.payload` 曾用 `JSON.stringify(... )::jsonb`，在 postgres.js 缓存预处理语句后会发生二次 JSON 编码，导致下一轮 `payload->>` 读不到结构化事项。现在统一用 postgres.js `json()` 写入真正 JSONB 对象，并有免费回归哨兵。
- 轻量会话引用不另建“记忆中心”：功能问答里的「刚才」只读取**当前住户本人**最近 72 小时内、且仍是本人上一条入站话题的结构化 `unsupported` 条目。查询在 SQL 层按 `personId` 与 household 收窄；别的住户插入决定不会顶掉本人引用，本人中途谈过别的事则旧拒绝不再被误当作「刚才」。不读自由文本、不增加表、模型调用、提示词或出站能力。
- 免费闸最终为 168 项通过；tsc 仍只有既有 `speech-input.tsx` 两处 TS2717；未向真人发送短信。
- **旧 doctrine 作用面随功能逐项开放而收缩（策略摘要）**。功能前门已把「替住户对别人做事」这条线整体从旧主生成切出，受控路径根本不读旧 doctrine：
  - **命中已批准功能**：路由命中后由**被选中那一个功能**抽取本功能获准字段、写正文，再由纯代码投递——该轮 `toolsUsed` 为空、`promptComposition` 为 `null`，**旧 doctrine（`lib/ai/brains/coliving/doctrine/*.md`）与主生成大脑完全没有被装配**。
  - **统一产品功能问答**（`lib/chat/coliving/feature-qa.ts` + `feature-facts.ts`）：用户询问「为什么办不了 / 能不能做某事 / 你有什么功能」时，不要求必须紧接上一轮 `unsupported`；代码只选出相关的未开放事项事实与当前开放功能名，模型只负责自然表达，并由确定性 grounding 检查不得漏掉、歪曲或自行补充处理方案。该路径同样 `toolsUsed` 为空、`promptComposition` 为 `null`、**不读旧 doctrine**。以后开放新功能会从 `APPROVED_FEATURES` 自动进入回答，不为每个功能另写一套能力说明程序。
  - **只有这两条受控路径都没接住的请求**（不在清单里的主题、没点名收件人、普通聊天等）才落回**旧提示词大脑**——那时旧 doctrine 与主生成照旧装配、照旧约束这一轮。
- 因此**现在不要删掉整套 doctrine**：它仍是回退路径与大批普通对话的唯一约束，删除时机是受控路径覆盖到旧路径再无可兜之事，而不是现在。
