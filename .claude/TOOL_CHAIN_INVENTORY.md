# WillingLink 工具链与组合工具候选

> 建立日期：2026-09-09
> 状态：只读架构盘点，尚未改工具或生产行为。
> 目标：找出“模型知道该做什么，但因为工具太碎而漏动作”的高频链路。

## Doctrine 使用卡

- **现实问题**：新增工具后旧流程被挤掉；模型说已处理但没有完成联系；排班算对却漏通知、漏记录或转述走样。
- **适用 doctrine**：`always/constitution.md` 的承诺本轮兑现、每位受影响者收到自己那份；`always/arbitration.md` 的可执行与可持续；`domain/conflict.md` 的异步协调流程；`tool/records.md` 的动作留痕和跟进闭环。
- **业务不变量**：高频流程的关键完成条件不能依赖模型在多个细工具之间自行维持工作记忆。
- **承载层**：组合工具、事务状态和动作收据；模型保留价值判断与自然语言。
- **为什么不只改提示词**：历史已经证明工具列表增加后，原本写在描述里的“必须做”会被挤掉。
- **验收**：一次工具调用返回每位对象的投递、记录和待处理状态；部分失败不可伪装成全部成功。
- **停止条件**：如果组合工具只是把参数堆成一个更复杂的大表单、仍要求模型一次填完所有隐含状态，就停止合并。

## 当前工具面

`turn.ts` 当前定义 22 个工具：

| 类别 | 工具 |
|---|---|
| 交付与判断 | `sendReply`、`decide`、`logEvent` |
| 对外联系 | `contactPerson` |
| 规则 | `proposeRule`、`recordStance` |
| 冲突与排程 | `notePartyAffected`、`pickSchedule`、`chooseSchedule`、`recordShare`、`recordPosition`、`closeCase` |
| 后续 | `scheduleReminder` |
| 名册 | `addResident`、`confirmRoster`、`renamePerson` |
| 记忆与调查 | `remember`、`noteObservation`、`recall`、`lookupHistory`、`findSimilarCases`、`checkEnvironment` |

运行时会按模块裁剪，不是每轮都暴露 22 个；但复杂冲突仍会同时出现多个相近工具。

## 链路 1 · 多人排程发布

典型链路：

```text
收集/读取各方约束
→ pickSchedule
→ chooseSchedule
→ contactPerson × 其他参与者
→ recordShare × 每位参与者
→ notePartyAffected / recordPosition（按案情）
→ sendReply
```

**历史证据**：

- 算法算对但最终短信没有照抄；
- 调了 `pickSchedule` 却没选定候选；
- 联系多人时漏掉一个或几个参与者；
- `toolsUsed` 曾漏记补发路径，导致验收看不见实际动作；
- 工具输入的人或偏好错，结构检查只能证明输出与错误输入一致。

**组合候选 A：`publishSchedulePlan`**

输入只接收已经由 `chooseSchedule` 选定的 `planId`、案件 id 和必要的简短沟通意图；代码从权威候选读取参与者与时段，原子完成：

- 给每位受影响者生成“其本人时段”的结构化消息槽位；
- 逐人投递；
- 记录份额和受影响者；
- 返回逐人的 `delivered / blocked / failed` 收据。

模型仍负责：为什么选择这个候选、是否接受算法第一名、最终自然措辞。模型不再重复填写已经算好的时间。

**主要风险**：如果组合工具自己生成最终短信，就会重新夺走“大脑是唯一作者”；应只提供结构化权威槽位或让统一写话层生成，不能硬编码完整话术。

## 链路 2 · 新住客加入并首次联系

典型链路：

```text
addResident × 人数
→ contactPerson × 新人
→ 必要时 remember / renamePerson
→ sendReply 给报号码的人
```

**历史证据**：新增四个工具后，模型调了 `addResident` 却漏掉首次联系；后来依靠代码级补发兜底。

**组合候选 B：`addResidentsAndIntroduce`**

- 一次接收多个号码；
- 添加成功的人自动进入待首次联系清单；
- 每个人独立返回添加与投递状态；
- 联系文本仍由写话层按 tenancy SOP 产生。

**优先级判断**：中。该流程已有强制补发保护，当前不是最痛点；除非工具盘点发现现有兜底显著增加模型往返或仍常失败，否则不先重构。

## 链路 3 · 普通冲突建案并听取另一方

典型链路：

```text
logEvent(openCase)
→ recordPosition
→ notePartyAffected
→ contactPerson
→ scheduleReminder（需要等待时）
→ sendReply
```

**风险**：开案、记录来源、标记受影响人和联系对方是同一个业务动作的多个技术步骤；任一步漏掉，后续 context 就会残缺。

**组合候选 C：`startConflictFollowup`**

输入：报告内容、被谈到的人、影响、需要向对方确认的一个问题、披露边界。

原子完成：

- 建案或复用现有案件；
- 记录为 `party_claim` 并保留来源；
- 标记受影响者；
- 经隐私边界检查后联系目标；
- 创建等待状态；
- 返回案件与投递收据。

**主要风险**：`被谈到的人`、`披露边界` 和“该问什么”需要语义判断；若输入 schema 太大，模型仍可能填错。应先由现场卡验证这些字段稳定，再决定是否实现。

## 链路 4 · 共同规则形成

典型链路：

```text
proposeRule
→ contactPerson × 尚未表态者
→ recordStance（后续多轮）
→ 调整或宣布成立
→ 必要时 scheduleReminder
```

**组合候选 D：`circulateRuleProposal`**

- 只接收规则草案 id；
- 代码读取实际受影响者和已有表态；
- 只联系尚未表态的人；
- 返回谁已同意、谁反对、谁待回复；
- 不把“已发送”写成“已同意”。

**优先级判断**：中高。它能直接解决“何时算成立”的 doctrine 拉扯，但需要先确认参与范围，不能把名册自动当全屋。

## 链路 5 · 红区停止与保留事实

典型需求：

```text
识别客观红区
→ 停止危险外发
→ 保存已确认事实与用户要求
→ 给当前用户简短说明能力边界
→ 如存在明确接手者再交接
```

**组合候选 E：`stopAndPreserve`**

这个候选不应急着实现成万能“升级工具”。当前连人工接手者和通道都没定，先把停止原因、禁止动作和保留事实做成结构化状态更实际。

## 优先级对照

| 候选 | 已有真实失败证据 | 对模型减负 | 语义参数风险 | 当前优先级 |
|---|---:|---:|---:|---:|
| A 发布排程方案 | 高 | 高 | 中 | 1 |
| C 开启冲突跟进 | 高 | 高 | 高 | 2（依赖现场卡） |
| D 分发规则草案 | 中 | 中 | 中 | 3 |
| B 加人并首次联系 | 高，但已有兜底 | 中 | 低 | 4 |
| E 停止并保留 | 方向明确、通道未定 | 中 | 高 | 暂缓 |

## 当前结论

- 工具数量本身不是唯一问题；真正危险的是一个业务承诺跨越 5–10 个可独立失败的调用。
- 第一组合候选是 `publishSchedulePlan`，因为权威候选、参与者和时段已经由代码知道，最适合减少模型重复转述与漏动作。
- 但第一项总体产品实验仍不一定选工具：现场卡和 Golden Trace 更直接覆盖最近的角色、隐私和冗长问题。
- 做选择前先完成一张三方案对照，不因任何一条工作线刚写完就偏向它。
